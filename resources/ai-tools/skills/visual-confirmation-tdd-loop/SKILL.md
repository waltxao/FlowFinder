# Visual Confirmation → TDD Loop

## Overview

先核实现状（含行为接线证据），再把「可视化确认」放在 TDD 之前：每轮只解决一个用户能看见的取舍，用可切换的对比稿代替文字想象；定稿后单独取得实现授权，再按 SPEC/PLAN、失败测试先行、桌面实测和文档同步推进。它不替代 TDD 技能，只补齐现状核验、确认、授权、验证边界四段。

## When to Use

使用：

- 用户要求「先做可视化再让我选」「一次只问一个」「确认前先问我」「以后所有确认都要可视化」。
- 用户问「这是什么」「现在是什么样的」「在哪设置」，或方案依赖「是否已实现 / 是否接线」。
- UI/UX、布局、顶栏、侧栏、标签、详情栏、图标、字号、间距存在多个可选方向。
- 设置页、开关、默认值、选择器、删除/移动/覆盖等行为型取舍。
- 用户要求把可视化确认与 TDD、SPEC/PLAN、桌面实测、台账更新串成闭环。
- 实现后需要真实窗口截图、像素测量、AX/Computer Use 取证，或遇到 TCC、坐标失效、分隔条拖不动。
- 已有 TDD 技能，但视觉或行为决策尚未锁定。

不使用：

- 纯后端、数据、脚本任务，且没有用户可见的视觉或行为取舍。
- 规格已完整、方案唯一，只差编码。
- 只需要解释代码或回答事实问题。
- 用户明确要求跳过确认；记录豁免，但仍保留测试与验证纪律。

## Iron Rules

1. 先读现状，再提问；能用代码或文档回答的问题不要问用户。
2. 一次只问一个问题；多个待决项排队，不在一轮打包。
3. 视觉取舍先出可切换对比稿；不要用纯文字选项让用户想象。
4. 选中选项不等于写入授权；实现前单独问一次「可以进入实现吗」。
5. 规格未锁定不写实现；没有失败测试不算实现。
6. 未复现的 bug 不宣称修复；未做的验证不宣称通过。
7. 用户选了什么就实现什么，不偷偷换回推荐项。
8. 改代码同一轮更新 SPEC/PLAN/CHANGELOG/HANDOVER/需求台账（若项目有）。
9. 真实窗口结论必须附窗口号、截图路径、测量值或 AX 状态；没有证据不写「对齐」「通过」。
10. 坐标点击前必须在同一执行内重新截图并换算几何；跨调用不复用坐标。
11. 系统 TCC 权限只能由用户本人授权；不代点、不循环重试。应用自己的跳过开关不等于系统授权。
12. 临时修改偏好、窗口或分栏状态前记录原值；验证后恢复，只操作自己启动的验证实例。
13. 判断「未接线 / 已实现 / 缺失」前，必须同时核验常量键、裸字符串键、默认值、读写方和用户可达路径；只查一路视为未核验。
14. 行为型取舍（开关、默认值、删除/移动等风险操作）的对比稿必须含「现状行为矩阵 + 每个选项下各操作的弹窗/提示 mock」；只画静态控件不合格。
15. 用户问「现在是什么样的」时，先给现状可视化再给选项；新事实推翻前提时，作废旧选项、重新出稿再问，不沿用旧标签。

## Workflow

| 阶段 | 动作 | 产物 | 门禁 |
|---|---|---|---|
| 0 现状 | 读文档、代码、当前界面；对行为型项做四路核验（常量键/裸字符串/默认值/读写方+路径） | 事实表（含 file:line）与问题清单 | 每个「已接线/未接线」都有证据；「待验」不当事实 |
| 1 确认 | 一次一问 + 可切换对比稿 | 决策台账 | 每个视觉/行为取舍都有用户选择 |
| 2 锁定 | 置信度清单 + 单独 go/no-go | 定稿摘要 | 用户明确「进入实现」 |
| 3 规格 | 写 SPEC/PLAN | 数值、状态、验收、人工项 | 规格无未决项 |
| 4 红 | 每个行为一个失败测试 | 红色测试输出 | 先红后绿 |
| 5 实现/验证 | 最小实现 + 全量测试 + AX/点击/压测 | 可复核证据 | 证据包齐全（窗口号/截图/测量/AX/未验项）；未复现不宣称修复 |
| 6 收口 | 更新文档/台账/基线 | 当前验证数字 | 同轮同步，不留到下一轮 |

## Phase 0 — Ground

1. 读项目指令（如 `AGENTS.md`、`CLAUDE.md`、`QODER.md`）、交接文档、需求台账、现有 SPEC/PLAN、CHANGELOG 和相关代码。
2. 记录当前界面与当前度量：截图、AX 状态、真实窗口比例；覆盖单/双栏、侧栏显示/隐藏、全屏、主题等真实状态。
3. 列出问题清单，区分「已确认」和「疑似」；能定位到文件/行号就定位。
4. 能通过阅读回答的问题不要问用户。

### Phase 0.1 — 行为事实核验（设置/开关/风险操作强制）

1. 列全候选项：设置行、默认值、孤儿键、只写不读的偏好、同类重复控件。
2. 四路 grep，缺一不可：
   - 常量/枚举键（如 `FFUserDefaultsKeys.*`）；
   - 裸字符串键（源码、plist、`@AppStorage`、`register(defaults:)`）；
   - 默认值与写入点；
   - 读取方、生效条件、守卫；风险操作再查确认弹窗/Sheet/Alert 的调用点。
3. 核用户可达路径：控件是否在已发布界面、是否被隐藏、从哪个入口进入。
4. 输出事实表：`项 | 常量键 | 裸字符串 | 默认值 | 写入方 | 读取方 | 用户路径 | 结论 + 证据(file:line)`。
5. 结论只写「已接线」「未接线」「待验」；「待验」不得驱动选项，也不得当成事实告诉用户。
6. 具体 grep 配方、矩阵与反模式见 `references/behavior-state-audit.md`。

## Phase 1 — One Question, One Visual

1. 选择当前最阻塞后续工作的一个决策。
2. 视觉取舍必须做可切换对比稿：现状 + 2–4 个互斥选项，一轮只测一个轴。
3. 行为型取舍（开关行为、默认值、删除/移动/覆盖等）的对比稿还必须包含：
   - 现状行为矩阵：操作 × 当前结果 × 证据；
   - 每个选项下的操作结果 mock，至少覆盖删除、移动、双击/打开，按功能裁剪；
   - 若已有同类控件或确认弹窗，现状区必须并列展示，避免重复控制。
4. 使用真实窗口比例和真实状态切换，标注数值与基线；不要用缩略卡片掩盖问题。
5. 提交前逐项自检：每个选项都能切换、选中态同步、控制选择器只作用于控件、键盘可用、无控制台错误。详见 `references/switchable-comparison.md`。
6. 只问一个问题；选项标签与对比稿完全一致；不要在正文附带第二个问题。
7. 把回答写入决策台账，记录用户原话约束，而不是只记选项字母；行为型项同时记录现状证据与 file:line。
8. 按回答类型继续：
   - 「先做可视化」→ 停止提问，先出对比稿。
   - 「这是什么 / 现在是什么样的」→ 先给现状可视化（控件 + 真实行为矩阵），再问一个选项问题。
   - 「选 A，但 X 要改」→ 记录 A + 细化项，下一轮只问 X。
   - 「你推荐哪个？」→ 给出推荐与权衡，让用户确认，不替用户决定。
   - 「没办法调整 X 吗？」→ 当成约束问题，追加诊断或新对比稿，不硬塞原选项。
   - 「都不对」→ 回到现状审计，追问具体痛点，不造新模型。
9. 新事实推翻前提（例如发现同类开关或确认弹窗已存在）时：停止沿用旧选项，把台账标「作废（前提变更）」，重新出稿并重新只问一个问题；不得把新事实硬塞进已选方案。
10. 重复，直到置信度门禁通过。问题协议与台账模板见 `references/confirmation-loop.md`。

## Phase 2 — Confidence Gate and Implementation Authorization

逐项确认：

- [ ] 所有用户可见决策已记录，含单/双栏、侧栏、全屏、主题等状态。
- [ ] 行为型项的现状矩阵与操作 mock 已核对；没有「待验」结论被当成事实。
- [ ] 数值指标、边界状态、交互行为写清楚。
- [ ] 版本号、删除/迁移范围、破坏性操作已明确授权。
- [ ] 验收测试与人工确认项已列出。
- [ ] 没有「推荐但未选」的项被带入实现。
- [ ] 台账中没有被新证据作废却仍被引用的选项。
- [ ] 用户已在下一条消息中明确回答「可以进入实现」。

然后只问一个问题：「按这份定稿进入实现吗？」

对比稿里的点击、界面上的采纳、推荐项的默认值都不算写入授权。

## Phase 3 — Spec and Plan

写 SPEC，至少包含：

- 锁定决策（逐条对应决策台账）
- 数值指标
- 状态矩阵
- 行为规则
- 非目标
- 验收标准
- 人工确认项
- 验证边界
- 未决问题（必须为空才能进入实现）

写 PLAN：

- 有序任务
- 涉及文件
- 测试名
- 红/绿命令
- 依赖与验证方式

版本或范围变更单独确认；不替用户假设语义版本。模板见 `references/spec-test-verify.md`。

## Phase 4 — Failing Test First

1. 一个行为一个测试；先写会失败的测试。
2. 运行并记录红色输出；没有看到红，不写实现。
3. 纯几何、度量、策略逻辑优先抽成可测函数；避免只用截图验证。
4. 写最小实现，让聚焦测试变绿。
5. 跑全量套件；全绿后再重构。
6. 项目有自检/断言 harness 时，与单元测试一起扩展，记录精确数量。
7. 遵循项目现有的 TDD 技能（如 `grillme-matt:tdd`、`superpowers:test-driven-development`），不要另起一套。

## Phase 5 — Build and Verify

1. 构建一个可识别的版本；防止同时存在多个可启动副本；核对版本字符串。
2. 走通黄金路径和边界：侧栏显示/隐藏、单/双栏、全屏、拖标签、关闭按钮、+ 新建标签、拖回原目录。
3. 自动化优先：纯几何、状态转换用测试；真实窗口用 AX + 截图 + 物理点击；概率性问题做 10–20 次布局切换压测。
4. 原生 macOS 真机取证：加载同用户目录的 `macos-app-ui-verification`，按它的脚本和命令执行；本 Skill 只规定门槛：
   - 用 `CGWindowList` 取窗口 id 与 bounds，再用 `screencapture -x -o -l<id>` 截目标窗口；截图不依赖窗口在前台。
   - 对齐不靠目测：用 `NSBitmapImageRep` 或配套脚本逐像素测两个控件的中心线/边距，报告 pt、规范值和误差。来源案例：红绿灯中心 17.5pt = 活动标签文字中心 17.5pt，规范 18pt，误差 0.5pt。
   - 截图坐标与窗口点坐标可能不同（来源案例：截图 1416×768，窗口 1660×900）；先按截图尺寸换算，再点击。
   - 坐标点击遵循「同一执行内 `getScreenshot` → 换算 → 点击 → 再截图复核」；跨调用不复用坐标。报 `Screenshot coordinates require a current screenshot...` 时重新绑定窗口与状态，不要盲重试。
   - 报 `The user is still interacting...` 时立即让出控制，等用户操作结束再重新取状态；不要循环抢占焦点。
   - TCC 弹窗会让 Computer Use 超时。先截全屏确认弹窗；由用户本人在系统弹窗点「允许」或去系统设置授权。`FF_SKIP_PERMISSION_GATE=1` 这类应用开关只跳过应用自己的权限门，挡不住 TCC；不得代点，不要循环重试。
   - 合成拖拽改不动 `NSSplitView` 分隔条时，改为确定性状态复现：退出自己启动的实例 → 记录原值 → `defaults write <bundle-id> <key> <value>` → 重启 → 截图 → 恢复原值并重启。只操作自己启动的实例；用户正在用的实例需先征得同意。
5. 采集证据包：窗口号、owner、bounds；截图路径、图像尺寸与 scale；测量值/规范值/误差；AX 元素或状态；点击/拖拽序列；未验项。格式见 `references/spec-test-verify.md` 的 Native Desktop Evidence。
6. 不能复现时，报告「未复现」并附操作序列/证据；不要宣称修复。把已确认的结构问题单独列出。
7. 像素观感、hover、真实拖拽手感、TCC 相关项等自动化看不到或无权操作的项，列入人工确认清单。
8. 恢复临时偏好和窗口状态，退出自己启动的验证实例；截图路径和实测数字同轮回写台账/HANDOVER。

## Phase 6 — Closeout

1. 跑全量测试 + 自检；记录精确命令、输出、日期、范围。
2. 同轮更新 SPEC/PLAN/CHANGELOG/HANDOVER/需求台账（若存在）；证据包（窗口号、截图路径、实测值）一并写入；旧基线标为「当轮实测值」。
3. 报告：改了什么、证据是什么、哪些未验证/未复现、临时状态是否恢复、还有哪些开放决策。
4. 没有测试失败、人工项未验或 bug 未复现时，不使用「完成/修复」这类无范围声明。
5. 提交/推送只在用户明确要求时执行。

## Visual Comparison Minimum Standard

- 现状 + 2–4 个互斥选项；一轮只回答一个轴。
- 真实窗口比例与真实状态切换，不用缩略卡片掩盖问题。
- 标注具体数值和基线，例如中心线、间距、避让量。
- 选项按钮标签与提问标签完全一致；选中态清晰可见。
- 提交前逐项点击自检；事件选择器限定在控件内。
- 无外部网络资源、无控制台错误、目标尺寸无溢出。
- 行为型对比稿必须含现状行为矩阵与每个选项下的操作结果 mock，不能只画静态控件。
- 现状结论必须能回溯到 file:line 或运行证据；没有证据只能写「待验」。
- 对比稿只用于检查；确认在对话中完成。

## Source Evidence

来源案例：FlowFinder 0.8.0 Beta（2026-10-21）。

- 6 轮可视化定稿：标签形态 A → 接缝 A1 → 顶栏解剖图 → 紧凑 30pt 带 + 不动红绿灯 → 全局顶栏 → C2 六 pt 空条。
- 用户纠正：纯文字选项被拒绝；要求「以后所有需要我确认都要做可视化」；对比稿 A2/A3 无法切换；用户没有选推荐项；版本从 0.9.0 被纠正为 0.8.0 Beta；详情栏要求「在现状上改」而不是换新模型。
- 对比稿切换失败根因：根节点 `data-style` 被 `closest` 抢先命中；改为只匹配控制按钮后恢复。
- 来源会话报告：`make swift-test` 301 条 0 失败；`FF_SELFTEST=1` 153 项 0 失败。以上为来源报告值，未在本 Skill 创建过程中重跑。
- 人工残留：A1 肩线像素观感、hover、真实拖拽手感因屏幕录制权限缺失未自动验证。
- 12 项后续需求在来源会话结束时仍在确认中；本 Skill 不宣称该部分已完成。

### 扩展案例：FlowFinder R-20（2026-10-21 → 2026-10-22）

来源会话：`8e8ea484-01b5-4565-8e7c-e1034f1d68a1`。

- 失败：Computer Use 两次超时（macOS TCC「访问桌面文件夹」）；坐标点击报 `Screenshot coordinates require a current screenshot...`；多次 `The user is still interacting...`；合成拖拽未改变 `NSSplitView` 侧栏宽度。
- 成功：`CGWindowListCopyWindowInfo` 取窗口 id（14608 / 14645 / 14675），`screencapture -x -o -l<id>` 截目标窗口；`NSBitmapImageRep` 逐像素测量红绿灯中心 17.5pt = 活动标签文字中心 17.5pt（规范 18pt，误差 0.5）；重新取窗口状态和截图后再操作，不复用旧坐标。截图 `/tmp/ff-toolpage-26102202.png`、`/tmp/ff-narrow-180.png`。
- 状态复现：`defaults write com.flowfinder.native sidebar_width -float 180` → 重启 → 截图；随后恢复 206 并重启。
