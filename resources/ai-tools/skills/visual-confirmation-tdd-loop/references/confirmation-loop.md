# Confirmation Loop

## Purpose

把「问用户」变成可复用的确认协议：一次只问一个，视觉取舍先看得见，回答落进台账，定稿与实现授权分开。

## One-Question Protocol

- 每轮只问一个问题。使用一次 `AskUserQuestion`，其中只放一个 question 对象。
- 不要在正文补第二个问题，也不要用「顺便问一下」绕过限制。
- 多个待决项时，选最阻塞后续工作的那个；其余写入待办队列，等下一轮。
- 能通过读代码、文档、截图回答的问题不要问用户。
- 问之前先说明为什么要问，以及这个答案会影响哪个实现决策。

## Question Types

| 类型 | 用途 | 示例 | 是否必须可视化 |
|---|---|---|---|
| 诊断题 | 定位用户说的「难看/不对」具体指什么 | 「是这一行的图标、间距，还是整条基线？」 | 最好带标注图 |
| 选择题 | 在互斥方向中拍板 | 「A/B/C 三版，选哪版？」 | 是 |
| 细化题 | 已选方向后的子轴调整 | 「接缝用内凹圆角、柔和接缝还是微缝？」 | 是 |
| 行为题 | 开关行为、默认值、删除/移动等操作后果 | 「打开后删除和移动分别弹什么？」 | 是：现状行为矩阵 + 操作 mock |
| 范围题 | 版本、删除、迁移、非目标 | 「删除哪些旧副本？」 | 否，但必须给出路径和后果 |
| go/no-go | 定稿后是否进入实现 | 「按这份定稿进入实现吗？」 | 否，但先给定稿摘要 |

## Visual-First Rule

- 所有涉及视觉取舍的确认，必须先出可切换对比稿；没有对比稿就不要求用户选。
- 行为型取舍同样强制可视化：对比稿必须含现状行为矩阵与每个选项下的操作结果 mock；不能用文字选项替代。
- 用户问「这是什么 / 现在是什么样的」时，先给现状可视化（控件 + 真实行为 + 证据），再问一个选项问题。
- 非视觉、非行为的范围/版本决策可以用文字选项，但要写清具体版本字符串、路径、不可逆性和保留项。
- 不要用抽象标签代替后果，例如只写「全套」「只升版本」而不说明会删除什么、保留什么。
- 对比稿是检查工具，不是确认按钮；用户的对话回答才是决策来源。

## Option Design

- 2–4 个互斥选项；再加「都不对/继续改」。
- 包含「现状」基线，避免用户在没有参照的情况下选。
- 每个选项写清代价，不只写优点。
- 可以标「推荐」，但不能默认选中或替用户决定。
- 选项标签必须与对比稿里的标签逐字一致。
- 一轮只改变一个轴；不要在同一个对比里同时改颜色、间距和结构。

## Handling Answers

### 「先做可视化再让我选」

停止提问，先出可切换对比稿；不要继续用文字解释选项。

### 「这是什么，现有是什么样的」

先给现状可视化：控件形态、当前真实行为矩阵、file:line 或运行证据；然后再问一个选项问题。不要用文字描述代替。

### 新事实推翻前提

停止沿用旧选项；把台账标「作废（前提变更）」，记录新证据与重问轮次，重新出稿并重新只问一个问题。不得把新事实硬塞进已选方案。

### 「选 A，但 X 要改」

记录 A 为方向，X 为硬约束；下一轮只可视化 X，不重新问整个方向。

### 「你推荐哪个？」

给出推荐和权衡，但仍然让用户确认。推荐不等于用户选择。

### 「没办法调整 X 吗？」

这是约束问题，不是选择题。先回答能否调整、代价是什么；需要时追加诊断题或新对比稿，不要硬塞原来的选项。

### 「都不对」

不要继续造新模型。回到现状审计：问「具体是哪里不对」；如果是「和现有设计格格不入」，就在现有设计语言内做降噪/重构对比，而不是换一套模型。

### 用户点击了对比稿里的选项

只说明用户在看哪个方案，不构成写入授权。仍需在对话中单独确认；必要时复述「你选的是 X，我按 X 进入实现，确认吗？」

### 用户给出模糊回答

把模糊回答拆成一个可验证的约束，再问一次；不要自行补全用户没说的版本号、删除范围或视觉数值。

## Decision Ledger

| ID | 日期 | 问题 | 现状证据 | 选项 | 用户选择 | 原话约束 | 状态 | SPEC |
|---|---|---|---|---|---|---|---|---|
| D-01 |  |  |  |  |  |  | 已定/未定/作废（前提变更） |  |

规则：

- 只记录用户实际选择；推荐项不算已定。
- 「原话约束」保留数字、版本、路径和例外，不要只写「按用户要求」。
- 行为型决策的「现状证据」写 file:line 或运行记录；没有证据写「待验」，不能当结论。
- 状态只有「已定 / 未定 / 作废（前提变更）」；作废的决策保留记录，不要删，并写清新证据与重问轮次。
- 每个已定项都要能映射到 SPEC 的一个章节或验收条件。
- 实现前检查台账：没有「未定」项，也没有仍被引用的「作废」项，才能进入 Phase 3。

## Confidence Gate

逐项打勾后才能问 go/no-go：

- [ ] 所有用户可见决策已记录，含单/双栏、侧栏、全屏、主题等状态。
- [ ] 行为型项的现状矩阵与操作 mock 已核对；没有「待验」结论被当成事实。
- [ ] 数值指标、边界状态、交互行为写清楚。
- [ ] 版本号、删除/迁移范围、破坏性操作已明确授权。
- [ ] 验收测试与人工确认项已列出。
- [ ] 没有「推荐但未选」的项被带入实现。
- [ ] 台账中没有被新证据作废却仍被引用的选项。
- [ ] 用户已在下一条消息中明确回答「可以进入实现」。

go/no-go 只问一次，问完停止，不要在同一条消息里继续追问细节。

## Version, Scope, Destructive Actions

- 先确认精确版本字符串，例如「0.8.0 Beta」而不是「下一个大版本」。不要替用户假设语义版本。
- 删除或移动前列出具体路径、数量和保留项；让用户选范围。
- 优先移到废纸篓或归档目录，不直接 `rm`。
- 保留当前运行副本和可恢复的构建；删除前确认没有未保存工作。
- 破坏性操作单独确认，不与视觉选择混在同一轮。

## Correction Log

- 记录用户原话，不转述成自己的总结。
- 把纠正转成后续轮次的硬约束；不要下一轮又回到被否定的方案。
- 用户说「以后都这样」时，写入项目纪律或本 Skill 的规则，而不是只记住这一次。
- 纠正涉及流程时，下一轮先复述新规则，再继续问。

## Worked Example

FlowFinder 0.8.0 Beta（2026-10-21）的确认顺序：

1. 标签形态：现状 + A 焊死式 / B 悬浮胶囊 / C 极简文字 → 用户选 A，但要求调整接缝。
2. 接缝：A1 内凹圆角 / A2 柔和接缝 / A3 微缝悬浮 → 对比稿切换失败，修复后用户选 A1。
3. 顶栏解剖图：编号元素 + 两条中心线 → 用户多选确认全部问题。
4. 中心线：36pt 全高 + 下移 2pt / 28pt + 下移 6pt / 紧凑 30pt + 不动红绿灯 → 用户选第三项，不是推荐项。
5. 全局顶栏结构：紧凑 + 所有元素共用中线 → 用户确认结构。
6. C1/C2：满高标签 / 6pt 空条 → 用户选 C2。

随后单独问「这版顶栏可以进入实现吗？」，用户回答「可以，按这版实现」，才进入 SPEC/PLAN 和失败测试。

关键教训：用户选 A 不代表接受 A 的接缝；用户没有选推荐项时，以用户选择为准；对比稿自身有 bug 时，先修工具再问。

设置接线的补充案例（2026-10-21）：只按常量 grep 判 9 个设置失效 → 用户要求现状可视化 → 裸字符串检索发现 2 个已接线、删除确认已存在 → 作废「删除 + 移动」并重问。详见同目录的 `behavior-state-audit.md`。
