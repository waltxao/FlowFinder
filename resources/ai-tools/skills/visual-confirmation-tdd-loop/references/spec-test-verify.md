计划中的每个任务都应能在一次聚焦运行中验证；不要写「实现整个 UI」这种不可验证的任务。

## TDD Sequence

1. 选一个用户可观察的行为。
2. 写一个会失败的测试；测试名读起来像规格。
3. 运行聚焦测试，记录红色输出。
4. 写最小实现让测试变绿。
5. 跑全量套件；确认没有回归。
6. 全绿后再重构。
7. 下一个行为，重复。

规则：

- 没有看到红，不写实现。
- 不在红的时候重构。
- 不批量预写「想象中」的测试；用垂直切片。
- 纯几何、度量、策略逻辑优先抽成纯函数测试，避免只能靠截图验证。
- 测试期望值来自独立真相源：规格数字、手算结果、已知正确字面量；不要用代码自己算一遍再比较。
- 只测公共接口；重命名内部函数不应破坏测试。

## Verification Ladder

按顺序往上走，每层留下证据：

1. **纯逻辑/单元测试**：度量、几何、策略、排序、状态转换。
2. **集成/行为测试**：拖放、关闭、标签切换、布局切换。
3. **构建与启动**：编译、打包、版本字符串、单实例。
4. **AX / 窗口截图 / 像素测量 / 物理点击**：真实窗口中的黄金路径和边界。
5. **布局切换压测**：侧栏显示/隐藏、单/双栏、全屏、拖标签，连续 10–20 次。
6. **人工像素/手感/权限确认**：接缝观感、hover、拖拽手感、动画、TCC 或系统权限相关项。

不要用第 1 层的结果宣称第 4–6 层通过；也不要用截图宣称逻辑正确。

## Evidence Discipline

每次验证记录：

- 精确命令（例如 `make swift-test`、`FF_SELFTEST=1 ...`）。
- 精确输出（通过/失败数量、失败测试名）。
- 日期与代码范围（分支、提交或未提交状态）。
- 是「本次独立运行」还是「来源报告值」。
- 旧基线标注为「当轮实测值」，不要与当前基线混用。
- 第 4 层真实窗口验证附 Evidence Packet；没有窗口号、截图路径和测量值的「对齐/通过」不算证据。

示例：

```text
2026-10-21: make swift-test → 301 passed, 0 failed
2026-10-21: FF_SELFTEST=1 → 153 assertions, 0 failed
2026-10-22: 红绿灯中心 17.5pt = 活动标签文字中心 17.5pt；规范 18pt，误差 0.5pt
人工未验：A1 肩线像素观感、hover、真实拖拽手感（屏幕录制权限缺失）
```

### Failure Handling

| 现象 | 根因 | 处理 |
|---|---|---|
| `Computer Use request timed out` 连续出现 | 系统 TCC 弹窗吞掉点击 | 截全屏确认；由用户本人授权；不代点、不重试 |
| `Screenshot coordinates require...` | 截图过期或窗口几何变化 | 同一执行内重新取状态与截图，换算后点击 |
| `The user is still interacting...` | 真人正在操作 | 立即让出控制，等用户结束后重新取状态 |
| 合成拖拽改不动分隔条 | NSSplitView 命中或事件被拦截 | 退出自己的实例 → 记录原值 → 写持久化键 → 重启 → 截图 → 恢复 |
| 像素扫描全为 0 | 区域、极性或裁剪原点错误 | 缩小区域，切换 dark/light，核对 origin 与 scale |

### Measurement Rules

- 先确认 scale：`scale = 图像宽 / 窗口宽`；Retina 常见 2x，1x 时 px 才等于 pt。
- 区域坐标用图像像素，不要混入窗口点坐标；`--origin` 用于裁剪偏移。
- 对齐判定必须比较两个控件的同一边距或共用中线，并写出规范值和误差；不写「看起来对齐」。
- 窗口不在前台时红绿灯会变灰；要测颜色先激活窗口，或改测文字/图标。

### State Construction and Restore

- 优先 AX 设置 splitter 值；失败再用应用自己的持久化键。
- 写入前记录原值；退出应用后再写，避免退出时回写覆盖；重启后截图。
- 验证结束恢复原值并重启；报告恢复前后的值。
- 只操作自己启动的验证实例；不关闭、不重启用户正在用的实例，除非用户明确同意。
- 系统权限弹窗只能由用户授权；应用级跳过开关不代表 TCC 授权。

## Documentation Sync

如果项目有对应文档，代码改动的同一轮更新：

- SPEC：锁定决策、状态矩阵、验收标准、验证边界。
- PLAN：任务状态、验证结果。
- CHANGELOG：用户可见变化。
- HANDOVER：接手入口、当前基线、未完成项。
- 需求台账：逐条需求状态与证据。

同步规则：

- 不把文档更新留到「下一轮」或「收尾时」。
- 当前验证数字写在顶部或总览；历史章节保留但标注为历史。
- 未验证/未复现项必须写进文档，不要只写在聊天里。
- 真实窗口证据包（窗口号、截图路径、测量值/规范误差、AX 状态）与结论同轮写入；临时状态恢复前后的值也记录。
- 文档中的版本号、路径、测试数量要与实际运行一致。

## Claim Discipline

安全写法：

- 「已实现 X，自动化测试 301 条 0 失败；Y 因权限缺失未自动验证。」
- 「Z 问题连续 20 次布局切换未复现；已确认的结构问题是 W。」
- 「规格与计划已写入 A、B；代码未提交。」

避免：

- 「全部完成」——当还有人工项或未复现 bug。
- 「已修复」——当根因未确认或问题未复现。
- 「测试通过」——当只跑了部分测试或没有记录输出。
- 「视觉没问题」——当只做了代码检查。

## Source Case

FlowFinder 0.8.0 Beta（2026-10-21）的来源会话报告：

- `make swift-test`：301 条 0 失败。
- `FF_SELFTEST=1`：153 项 0 失败（决策表 71 / 区域 7 / 行为 4 / 焊接 35 / 侧栏避让 4 / 外壳 22 / 落点 10）。
- 中间阶段曾报告自检 137 项；后续扩展到 153 项。记录当前值，不把中间值当最终基线。
- 已做 AX/物理点击：+ 新建标签、红绿灯关窗、隐藏侧栏首标签 112pt、侧栏版本 0.8.0 Beta、双开检测。
- 未自动验证：A1 肩线像素观感、hover、真实拖拽手感（屏幕录制权限缺失）。
- 来源会话的 12 项后续需求仍在确认中；不能把第一轮 4 个问题的验证结果外推到全部 UI。

以上为来源报告值；本 Skill 创建过程没有重跑该项目测试。
