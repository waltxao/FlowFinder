# 需求 · 代码 · 测试三方漂移审计

## 用途

把“需求文档说做了什么”“开发台账说验到什么程度”“代码和测试实际做了什么”放在同一张证据表里，找出漂移、测试缺口和需要修改的地方。输出必须能直接排期，而不是只描述现象。

## 何时使用

- 用户要求结合需求文档和开发台账，审计所有功能点、测试覆盖或遗漏。
- 用户问“文档说完成但功能不可用”“台账和代码对不上”“上线前还有哪些风险”。
- 接手项目，需要先确认哪些需求是真的、哪些只是写在文档里。
- 快速迭代后，测试数、版本号、验收口径与代码状态可能脱节。
- 发版、交接、重构前需要一份带证据的基线。

## 不适用

- 单点 bug、崩溃、性能问题：先用 `superpowers:systematic-debugging`。
- 已知行为补测试：用 `superpowers:test-driven-development`。
- 改完代码后的台账/交接同步：用 `flowfinder-docs-sync`。
- 纯视觉设计取舍：用视觉确认类 Skill；本 Skill 只核对是否满足已写明的验收条件。

## 铁律

1. **文档是待验证声明，不是真值。** 代码、配置、运行证据优先；文档之间冲突时先标记，不自动选用最新一份。
2. **每条结论必须有证据。** 至少给出 `file:line`、命令输出或运行证据；找不到证据就写“未验”，不要写“应该”。
3. **区分五层事实。** 符号存在、有生产调用、用户可达、有行为测试、实机通过，是五个不同结论。
4. **审计阶段只读。** 不改代码、不改文档、不提交、不删除；修复必须等用户确认后另起批次。
5. **测试数量不是覆盖率。** 只断言几何、令牌、内部状态的测试不能证明业务闭环；应用内自检同样按行为判定。
6. **不沿用旧结论。** 来源会话、旧台账、记忆里的数字和判断都要在当前 commit 上重算或标“未验”。
7. **范围先全后深。** 先建立全量 ID 清单，再深挖 P0/P1；P2 可抽样，但必须写明抽样比例。
8. **结论可复跑。** 报告记录命令、日期、commit，让另一个人能按同样步骤得到同样结果。

## 输入

开始前确认以下信息；缺省时从仓库读取，但要在报告中写明来源。

| 项 | 说明 |
|---|---|
| 仓库根目录 | 所有路径的基准 |
| 文档集 | 需求、验收、台账、交接、最新 SPEC/PLAN |
| 代码范围 | 生产代码、测试目录、FFI/头文件、Info.plist、构建脚本 |
| 当前基线 | commit、版本、工作区是否干净 |
| 验证命令 | 构建、测试、自检；先读 Makefile/脚本，确认是否会杀进程或改环境 |
| 审计范围 | 全量功能点，或指定旅程/优先级；默认全量 |

跑测试前先读构建脚本。FlowFinder 的 `make swift-test` 可能结束正在运行的 FlowFinder 实例；未经确认不要直接执行。

## 工作流

### 步骤 0 · 锁定审计基线

```bash
git status --short
git log -1 --format='%h %ad %s' --date=short
```

按以下顺序读文档，记录版本、日期、状态口径、测试基线和相互冲突：

1. 产品定位（PRODUCT / 同类文档）
2. 需求基线（REQUIREMENTS）
3. 验收标准（ACCEPTANCE）
4. 开发台账（REQUIREMENTS-LEDGER）
5. 交接文档（HANDOVER）
6. 最新 SPEC / PLAN

工作区不干净时，把未提交改动单独记录，不要把它当成已发布事实。

### 步骤 1 · 建立需求 ID 清单

- 按旅程（J1–J5）和横切项分组；同时收集验收 ID（L/T/V/D/O/S/F/K 等）和台账 ID（R-xx）。
- 每个 ID 记录：来源文档、需求原文、优先级、文档声称状态、声称实现位置、所属旅程、关联验收项。
- 检查：需求有但验收无、验收有但需求无、台账无落点、重复 ID、同一 ID 多处定义。
- 输出“ID 总数 / 各旅程数量 / 文档冲突数”。这是后续完整性的分母，不能省略。

### 步骤 2 · 逐条核验实现

对每个 ID 依次检查六项：

| 检查 | 问题 | 通过条件 |
|---|---|---|
| 1. 位置 | 文档写的文件/符号存在吗？ | 能在当前 commit 找到；行号可偏移但不能指向无关代码 |
| 2. 调用方 | 生产代码真的调用了吗？ | 排除定义、测试、注释、文档后仍有调用方 |
| 3. 用户可达 | 用户能通过菜单/按钮/快捷键/工具页到达吗？ | 从入口追到实际动作，中间没有断链或禁用 |
| 4. 数据闭环 | 写入后有人读取并应用吗？ | 设置键有非 UI 读取方；FFI 有应用调用；通知有观察者；任务有消费方 |
| 5. 平台约束 | 权限、沙盒、无障碍、签名是否满足？ | Info.plist/entitlements 与 API 匹配；自定义控件有 AX 身份和操作方式 |
| 6. 限制与占位 | 是否被硬编码上限、禁用卡、空实现卡住？ | 限制可见、可配置，或文档明确写“本版不做” |

每项都要留下证据。静态找不到调用方时，先按“候选未接线”处理，再排查动态派发、selector、通知、反射和生成代码。

### 步骤 3 · 判定四类漂移

| 判定 | 典型证据 | 默认处置 |
|---|---|---|
| 文档过期 | 代码已实现/数值已变，文档仍写 ❌、旧值或旧入口 | 改文档；若同时无测试，追加“补测试” |
| 实现但无测试 | 用户可达，但没有行为级自动化；只有几何/令牌测试或完全无测试 | 补行为测试；UI 部分补实机证据 |
| 写了不生效 | 只写不读、FFI 无调用、入口无动作、权限键缺失、AX 不可操作、限制导致不可用 | 接线 / 删除 / 补权限 / 补无障碍 / 明确不做 |
| 完全未实现 | 无实现，文档描述准确 | 实现，或由用户确认移出范围 |

一个 ID 可以有主判定和附加标记，例如“文档过期 + 实现但无测试”。不要为了凑四选一而隐藏第二个问题。

证据等级统一写：

- 【断言】自动化测试或应用内自检，且断言用户可见行为。
- 【实机】截图、AX、日志、手工操作等运行证据。
- 【静态】只有代码/配置证据，未运行。
- 【未验】没有执行证据；不得写成“已完成”。

### 步骤 4 · 生成测试覆盖矩阵

先盘点所有测试与证据：

```bash
rg -n 'func test[A-Za-z0-9_]+' FlowFinder/Tests --glob '*.swift'
rg -n '#\[(tokio::)?test\]' rust-core/src
```

同时读取台账中的【实机】记录和自检日志。覆盖矩阵按旅程组织，至少包含：

| 列 | 内容 |
|---|---|
| ID / 旅程 | 需求编号与所属旅程 |
| 实现证据 | 生产代码 `file:line`，或“无” |
| 自动化证据 | `测试文件::用例名`，没有写“无” |
| 证据等级 | 【断言】【实机】【静态】【未验】 |
| 覆盖判断 | 完整 / 部分 / 仅手工 / 无 |
| 缺口 | 缺的是实现、测试、权限还是实机 |
| 建议测试名 | 可直接落地的行为测试名 |

判定规则：

- 只有断言用户行为的测试才算“完整”；只断言常量、几何、颜色、内部状态的算“部分”。
- 一个测试覆盖多个 ID 时全部列出，但不要把一个笼统的视图快照算作整个旅程。
- 手工证据与自动化证据分列，不能互相替代。
- 缺失测试名写成 `test<旅程><场景><预期>`，例如：
  - `testJ1PermissionGateShowsChineseGuidanceAndOpensSettings`
  - `testJ2SearchFindsFileBeyondThreeLevelsAndReportsTruncation`
  - `testToolPillIsAccessibleAsButtonAndKeyboardActivatable`

### 步骤 5 · 输出 P0/P1/P2 修改清单

| 优先级 | 判定 |
|---|---|
| P0 | 核心旅程断裂、虚假发布声明、权限/数据安全/无障碍阻塞、宣称可用但用户完全到不了 |
| P1 | 功能断开或只写不读、核心旅程缺行为测试、会误导发布的文档矛盾 |
| P2 | 死代码、无行为影响的文档漂移、边缘测试缺口、视觉/维护债 |

每条至少包含：

`优先级 | ID | 问题 | 证据（file:line / 命令） | 类型 | 处置 | 验收条件 | 依赖或需用户决策`

处置只用这些词：`接线`、`删除`、`补测试`、`改文档`、`补权限`、`补无障碍`、`人工验收`、`明确不做`。文档修改和代码修改分开标注，避免“改了文档就算修完”。

### 步骤 6 · 自检与交付

- 每个需求 ID 是否都有结论或明确“未审”。
- 每条结论是否有 `file:line` 或命令输出。
- 每个 P0/P1 是否有可执行的验收条件。
- 覆盖矩阵的分母是否等于 ID 清单总数。
- 测试数量是否来自本轮命令或明确标注“未重跑”。
- 是否列出了“未验/需人工确认”，而不是用推断填空。
- 是否确认没有改代码、文档或提交。
- 报告默认输出到对话；只有用户明确要求才写入 `docs/AUDIT-<date>.md`。

## 常见误判

| 误判 | 纠正 |
|---|---|
| FFI 零调用 = 功能为空 | 先查应用服务层、通知、任务队列和 UI 读取方；可能已由原生路径替代 |
| `setAccessibilityLabel` = 可访问 | 还要有 element、role、action、键盘焦点；label 只是朗读文本 |
| 测试全绿 = 需求完成 | 测试可能只覆盖几何/令牌；用户旅程需单独核对 |
| 文档写 ✅ = 已实现 | 必须给实现位置和验收证据；给不出就降级 |
| 符号存在 = 用户可达 | 追菜单/按钮/快捷键/工具页到实际动作，排除禁用和死入口 |
| 设置写了 = 生效 | 找非设置 UI 的读取方和 apply 路径 |
| grep 0 命中 = 不存在 | 排查动态派发、selector、通知、反射、生成代码；标“候选” |
| 测试总数一致 = 基线一致 | 可能只跑了部分测试；以本轮完整输出为准，否则标“未重跑” |
| 旧台账结论 = 当前事实 | 锚定 commit 重验；代码变了就以当前证据为准 |

## 完成检查清单

- [ ] 文档冲突、版本和基线已记录
- [ ] 需求 ID 清单覆盖所有旅程与横切项
- [ ] 每个 ID 至少完成“位置/调用方/可达性”三项检查
- [ ] 设置键、FFI、权限、AX 按数据闭环核验
- [ ] 四类判定没有混用，附加问题已标注
- [ ] 覆盖矩阵含具体测试名和证据等级
- [ ] P0/P1/P2 清单每条有证据和验收条件
- [ ] 未验项与需人工项单独列出
- [ ] 报告锚定 commit/日期，命令可复跑
- [ ] 审计期间未修改代码/文档/提交
