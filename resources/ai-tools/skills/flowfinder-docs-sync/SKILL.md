# FlowFinder 文档同步

## 何时使用

在 `flowfinder-native/` 内完成或准备完成以下任一变更时，立即使用本 Skill，不要留到下一轮：

- 修改 Swift / Rust 代码、资源、构建或行为
- 新增、修改、删除测试；测试总数变化
- 修改版本号、构建号、发布状态
- 确认或推翻设计决策、范围、验收口径
- 排查 bug 得到新的复现证据或根因
- 准备宣称「完成」、提交、推送、交接或发版
- 用户提到台账、交接文档、REQUIREMENTS-LEDGER、HANDOVER、CHANGELOG、SPEC、PLAN

范围仅限 FlowFinder 仓库；其他项目不要套用。

## 铁律

1. **同一轮完成。** 代码、测试、文档在同一轮改完；没有更新台账和交接，视为任务未完成。
2. **只写当次实测数字。** 数字必须来自本轮命令输出；旧数字、记忆里的数字、推断值都不能写入当前基线。
3. **单测不抬高总数。** 只跑了单个测试或部分测试时，不得更新 XCTest 总数；要么重跑全套，要么明确写「未重跑」。
4. **当前基线只有一个来源。** 当前 XCTest / 自检总数只维护在台账 §0 和交接顶部；其他轮次保留当轮数字并标注「当轮实测值」。
5. **状态不许含糊。** 只用 `已完成` / `部分完成` / `未开始` / `已废弃`。「设计完成但未实现」写 `设计进行中（未实现）`。
6. **证据分级。** 【断言】应用内自检 / XCTest；【实机】截图、几何日志、AX 或合成事件；【未验】只有代码，没有执行证据。代码在 ≠ 已完成。
7. **不擅自提交。** 默认只改工作区；用户明确要求提交/推送/发版时，按「提交、推送与 README」段执行，并回写真实提交哈希与推送状态。

## 文档职责

| 文件 | 职责 | 本轮至少检查 |
|---|---|---|
| `docs/REQUIREMENTS-LEDGER.md` | 唯一需求清单：ID、状态、实现位置、验证证据、已知限制 | §0 当前基线；对应 R-xx 行；历史数字标注 |
| `docs/HANDOVER.md` | 唯一交接入口：当前版本、分支、验证基线、§1.x 轮次、未验项、下一步 | 顶部元信息；新增/更新 §1.x；交接清单 |
| `docs/SPEC-*.md` | 已确认设计决策、开放项、验收口径 | 状态头；本轮决策；未决项 |
| `docs/PLAN-*.md` | 阶段、任务、执行状态 | 阶段勾选；验证步骤；状态头 |
| `CHANGELOG.md` | 未发版与历史版本变更 | 新条目或「未发版」段落；当轮验证数字 |
| `docs/PRODUCT.md` / `DESIGN-SPEC.md` / `ACCEPTANCE.md` | 产品取舍、视觉规格、验收标准 | 仅在需求、视觉或验收口径变化时更新，其他文档引用而非复制 |

不要新建 README、总结、迁移说明等旁支文档；需要沉淀的内容写进上述既有文件。

## 提交、推送与 README（2026-10-25 增补）

用户明确要求提交/推送后才执行；默认仍然只改工作区。

1. **预检**：`git fetch origin`；确认当前分支与 upstream；`git status --short` 分开「本轮改动 / 历史未提交 / 杂物」；`git diff --check`；扫描密钥（`sk-`、`ghp_`、`AKIA`、`PRIVATE KEY`）。
2. **不要整目录 `git add -A`**：显式列出路径；排除根目录截图、临时日志、`.DS_Store`、构建缓存；确需入库的 `resources/ai-tools/`、`scripts/`、`docs/images/` 取证单独确认。
3. **分组提交**：代码 + 测试 + 构建资源 / 文档（README、CHANGELOG、ledger、HANDOVER）/ 技能快照。每组数字来自当轮实测；全套未跑就写「未重跑」。
4. **推送前**：确认没有把桌面副本、DMG、`build/`、`DerivedData/` 带进去；大文件（>10MB）逐个确认是否确需入库。
5. **推送后回写**：把分支、远端、被推送功能提交的短哈希写入 HANDOVER 顶部/§1.x 与台账 §2.5 C；文档提交本身单独提交并再次推送，哈希写功能提交而非文档提交自身。
6. **README 同轮检查**：版本/构建徽章、当前分支、最新 Release 与资产名（以 `gh release view` 为准）、更新日志新增段、主图路径、测试基线、AI 资源入口。
7. **技能快照**：更新 `resources/ai-tools/MCP-AND-SKILLS.md` 的日期与条目；项目副本与运行时副本保持一致（先改运行时，再整目录拷贝，或反之但必须 `diff -rq` 验证）。
8. **公开仓库隐私**：真机审计截图常含个人文件名/桌面内容，默认不入库；只提交经过确认的 README 配图。文档里引用本地证据时标注「本地取证，未随公开仓库上传」。

## 真机验证补充（2026-10-25）

- **AX/CGEvent 修饰符**：用 `CGEvent` 发 ⌘A 后若 keyUp 丢失，Command 会残留，后续键入被当快捷键（曾误开任务中心）。收尾发 keyUp 55/54，并观察 `AXTextField` 值是否真的变化。
- **双栏搜索**：范围「双栏」时两侧输入框同步、各自过滤当前目录；「本栏」时两栏解耦。验证时先设范围再输入，避免把焦点切换当成搜索失败。
- **收藏右键**：用临时收藏目录验证 6 项（显示简介/新标签页/新窗口/上移/下移/从边栏移除），结束删目录、移收藏、核对 `SidebarFavorites`。
- **已知未修问题**：外部删除已选目录并刷新后，详情栏仍残留已删项（清空 `AXSelectedRows` 不消失）；末项「下移」菜单项未置灰。验证时不要误判为测试数据问题。

## 工作流

### 步骤 0 · 读当前真值

1. 读台账 §0 与最近 1–2 条 R-xx，记录旧基线与未验项。
2. 读交接顶部与最新 §1.x，记录当前版本、分支、验证基线。
3. 读本轮相关 SPEC / PLAN 的状态头。
4. 在仓库内跑 `git status --short` 与 `git diff --stat`，确认本轮实际改动面，避免只按记忆写文档。
5. 若仓库可能被其它会话并行修改，写前重读目标段落；不要用几分钟前的快照覆盖更新后的文档。

### 步骤 1 · 跑验证并保存原始输出

按改动面选择，不能省略与改动相关的项：

```bash
make version          # 版本唯一真源：Xcode 工程，不从文档推断
make build            # 代码/资源/构建改动后必须
make swift-test       # Swift 改动后跑全套；从 "Executed N tests" 取总数
make rust-test        # Rust 改动后
FF_SKIP_PERMISSION_GATE=1 FF_SELFTEST=1 \
  "$HOME/Library/Caches/FlowFinderBuild/Products/Debug/FlowFinder.app/Contents/MacOS/FlowFinder"
```

- 自检日志在 `/tmp/ff-debug.log`；以日志里的汇总为准，不要手算或复用旧值。
- 记录命令、日期、通过数、失败数、失败项。失败就不写「已完成」。
- 只有单项测试结果时，明确记录「仅跑单项，全套未重跑」。

### 步骤 2 · 更新台账

1. 找到对应 R-xx；没有就新增，编号接续。
2. 写清：需求原文、实现位置、验证证据（含本轮数字与日期）、未验项、状态。
3. 更新 §0 的当前基线；若总数变化，同时更新分层表。
4. 历史轮次数字不改写，只加「当轮实测值」语境。
5. 已废弃的需求保留行，状态改 `已废弃`，不要删除历史。

### 步骤 3 · 更新交接文档

1. 顶部：当前版本、分支、验证基线、代码规模（若变化）。
2. 新增或更新 `§1.x` 轮次：本轮做了什么、改了哪些文件、测试与自检数字、已确认决策、已知问题、未验项。
3. 更新「一句话现状」与接手清单；确保下一个人不用读聊天记录就能继续。
4. 交接里不写「应该没问题」；只写实际命令、实际结果和明确未验项。

### 步骤 4 · 按需同步 SPEC / PLAN / CHANGELOG

- 设计决策变化：更新 SPEC 状态头、决策条目、开放项，并回链台账 R-xx。
- 计划推进：PLAN 勾选完成项、更新状态头与验证步骤；未执行的阶段保持未勾选。
- 行为、版本、发布状态变化：CHANGELOG 增加「未发版」条目或新版本段；历史条目保留当轮数字。
- 只有文档结构、链接或状态变化时，才动 PRODUCT / DESIGN-SPEC / ACCEPTANCE；不要顺手重写。

### 步骤 5 · 一致性与覆盖自查

```bash
grep -nE "XCTest|FF_SELFTEST|自检总量|验证基线|当前总览|当前基线|为准" docs/REQUIREMENTS-LEDGER.md docs/HANDOVER.md
git diff --numstat -- docs/ CHANGELOG.md
```

逐项确认：

- 台账 §0、台账顶部说明、交接顶部、交接同步纪律段、本轮 §1.x 五处的当前数字完全一致。
- 历史段落里的旧数字都有「当轮实测值」或轮次语境。
- 本轮每个代码/测试/行为改动都能在台账找到落点。
- `git diff -- docs/` 非空且覆盖全部改动；若为空，任务未完成。
- Markdown 没有整文件空白差异；必要时改用精确 Edit。
- 链接与文件路径真实存在。

### 步骤 6 · 汇报

只列：改了哪些文档、当轮实测数字、仍未验证项、是否提交。不要宣称「已提交 / 已推送」，除非确实执行且有输出。

## 常见失败

| 失败 | 后果 | 避免 |
|---|---|---|
| 加测试后只跑单测，总数仍写旧值 | 文档与代码漂移（曾出现 301 与 302 不一致） | 跑全套再写总数，或写「未重跑」 |
| 同步纪律段硬编码旧基线 | 顶部与说明互相矛盾 | 当前基线只写一处来源，说明段引用它而不复制数字 |
| 把历史数字当当前基线 | 接手方误判验证状态 | 历史段落标注「当轮实测值」 |
| 设计未实现写成已完成 | 交接方以为可验收 | 状态写「设计进行中（未实现）」 |
| 只更新交接漏台账 | 需求状态失去唯一清单 | 两份都改，缺一不可 |
| 只更新台账漏交接 | 接手方不知道从哪继续 | 两份都改，缺一不可 |
| 并行会话更新文档后仍用旧读取回填 | 覆盖别人的新数字 | 写前重读目标段落，按最新内容 Edit |
| 直接覆盖整篇 Markdown | 大量空白差异，难以审查 | 精确 Edit，`git diff --numstat` 复核 |
