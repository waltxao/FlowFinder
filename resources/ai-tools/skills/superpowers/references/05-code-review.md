# 代码评审（requesting / receiving code-review）

评审是计划与质量的守门员，分两段式进行。

## 请求评审（requesting-code-review）

**激活时机**：每个任务完成、进入下一个之前。

**做法**：
- 对照**实施计划**逐条检查：实现了吗？验证过了吗？
- 按严重度报告问题：
  - **Critical（阻断）**：不符合规格 / 会炸生产 / 丢了功能 → 必须修，否则不推进。
  - **Major**：明显质量债 / 可读性差 → 建议修。
  - **Minor**：风格 / 命名 → 可后续。
- 评审结论写给用户：通过 / 带问题通过 / 打回。

## 接收评审（receiving-code-review）

当**你**是被执行方、收到主代理或用户的反馈时：

- 把反馈当事实处理，不辩解。
- 区分「真的 bug」和「品味不同」，前者必改，后者可讨论。
- 改完回到对应任务的验证步骤，确认仍绿。
- 不在回复里顺手改无关代码（见 Surgical Changes 原则，karpathy-guidelines 技能）。

## 子代理两段式评审（用于 subagent-driven-development）

派给子代理的评审要求固定为两步：
1. **规格符合度**：产出是否匹配计划里的任务定义？
2. **代码质量**：可读性、DRY、YAGNI、命名、是否有不必要复杂度？

两段都过，任务才算完成。
