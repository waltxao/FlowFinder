# 测试驱动开发（test-driven-development）

强制 RED-GREEN-REFACTOR 循环。没有「先写实现再补测试」的捷径。

## 循环步骤

1. **RED（红）**：先写一个**描述期望行为**的测试，运行它，确认它失败（且是因为「功能还没实现」而失败，不是因为测试写错）。
2. **GREEN（绿）**：写**最少量的代码**让测试通过。不要顺手加测试没要求的特性。
3. **REFACTOR（重构）**：在测试保护下清理重复、命名、结构。重构后测试必须仍绿。
4. 提交。然后下一个循环。

## 铁律

- **测试前写的业务代码，一律删除**，从测试重新推导实现。
- 不允许「先实现、后补测试」来假绿。
- 一个循环只解决一个行为。

## 常见反模式（写入 references 是为了对照避免）

- 写测试只为凑覆盖率，不描述真实行为。
- 测试永远绿（没看过它红）＝ 测试没在守卫任何东西。
- 绿了之后不重构，留下技术债。
- 一个测试断言太多，失败时不知道哪坏了。

## 验证

每个循环结束跑 `测试套件全绿` 才算数。计划里的「验证」字段就来自这些测试。
