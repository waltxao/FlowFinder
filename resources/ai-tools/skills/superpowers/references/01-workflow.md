# 基础工作流详解

Superpowers 的本质是一条「强制按顺序走」的工程纪律。下面展开每一步该说什么、做什么。

## 1. 头脑风暴（brainstorming）

**激活时机**：用户提出任何开发类需求，且尚未给出明确规格。

**做法**：
- 用苏格拉底式提问把需求逼清，而不是立刻给方案。
- 一次只呈现一小块设计（用户读得完的长度），逐块确认。
- 探索至少 2 个替代方案，说明取舍。
- 把确认后的设计落成**设计文档**（design doc），作为下游输入。

**产出**：一份用户签字确认的设计文档。没它，不进下一步。

## 2. 开隔离工作区（git worktree）

**激活时机**：设计文档确认后。

**做法**：
- 在独立分支 / worktree 上工作，不污染主分支。
- 跑项目初始化 / 安装依赖，确认 `clean` 的测试基线（全绿或全空）。
- 任何后续改动都在这个隔离区里发生。

## 3. 写实施计划（writing-plans）

见 `02-writing-plans.md`。

## 4. 子代理驱动开发（subagent-driven-development）

**激活时机**：实施计划就绪。

**做法**：
- 每个工程任务派一个**全新上下文的子代理**，附带：任务说明 + 计划片段 + 两段式评审要求。
- 两段式评审：① 查是否符合规格；② 查代码质量（可读性、DRY、YAGNI）。
- 主代理只做编排与审查，不自己写业务代码，可连续自主跑数小时不偏离计划。

**备选**：`executing-plans` —— 分批执行 + 人工检查点，适合需要人在场的场景。

## 5. 测试驱动开发（TDD）

见 `03-tdd.md`。

## 6. 请求代码评审（requesting-code-review）

见 `05-code-review.md`。

## 7. 收尾开发分支（finishing-a-development-branch）

**激活时机**：所有计划任务完成。

**做法**：
- 跑完整测试套件，确认全绿。
- 向用户给出 4 个选项并说明后果：合并 / 开 PR / 保留分支 / 丢弃。
- 若用了 worktree，清理掉。

## 哲学底线

- 测试驱动：先写测试，永远。
- 系统化优于临场：流程取代猜测。
- 降低复杂度：简单是首要目标。
- 证据优于声称：宣布成功前先验证。
