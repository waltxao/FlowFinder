# 可视化需求确认

## 目标

把模糊需求转化为一组可追溯、可验收的决策：先只读审查，再用可视化呈现方案，每轮只问一个问题，用户确认后才写规格与实施计划。

这不是设计或开发技能。它是一道确认门禁，防止在需求未收敛时直接改代码。

## 适用与不适用

适用：

- 用户要求“先审查，再逐项确认”“一次只问一个”“确认要做可视化”。
- 用户要求“回到旧版”“恢复改造前的布局”“撤销一次失败改造”，需要先确定恢复边界。
- UI/UX 整改、信息架构调整、多方案取舍等存在多个相互依赖决策的任务。
- 写规格或实施计划前，需要先锁定范围、方案与验收标准。

不适用：

- 单一事实问答、明确的单点修复、已有批准规格的纯执行。
- 用户只要求代码审查且不涉及需要拍板的设计决策。
- 紧急故障处置；先恢复服务，事后再补确认。

## 硬门禁

1. **只读审查先行**：审查阶段只读取代码、文档、截图和运行界面，不修改项目文件，不执行会改变状态的命令。
2. **决策必须可视化**：不要让用户在纯文字选项里做界面或交互决策。每个待确认决策都要展示受影响的真实界面、流程或对比图。
3. **每轮只问一个问题**：一轮只关闭一个决策。不得把多个问题包装成“顺便确认一下”。
4. **选择不等于授权**：用户选方案、采纳推荐或说“可以”，只代表决策确认，不代表授权写规格、计划或代码。写文件前必须获得单独的明确授权。
5. **决策必须可追溯**：每个确认项都要有 ID、证据、落点、验收标准和状态，并能在最终规格中逐条对上。
6. **改动或回退先固定基线**：记录分支、HEAD、工作区状态、未提交与未跟踪文件、旧版截图或构建物。旧代码只通过 `git show <ref>:<path>`、`git log`、`git diff` 读取；默认外科式恢复，禁止 `git reset --hard`、`git checkout --`、`git clean` 或覆盖工作区。

## 每轮回复结构

固定按以下顺序输出，避免问题被淹没在长文里：

1. **本轮判断**：一到两句话说明当前进展和这一轮要关闭什么。
2. **可视化**：展示受影响界面或流程的前后对比、方案对比或状态序列。
3. **待确认问题**：只问一个，给出 2–4 个互斥选项，推荐项在前。
4. **决策台账**：新增或更新一行，写明已确认、待确认和受影响范围。

不要在问题后追加“如果没问题我就开始”。这句话会让用户误以为已经获得写入授权。

## 工作流

### 0. 框定目标

先用一张范围/目标图呈现你的理解：目标用户、核心任务、成功标准、非目标、参考产品、约束条件；再提出一个确认问题。

从代码、文档和历史记录能查到的事实，不要拿去问用户。只有会改变方案走向且无法从现有材料判断的问题，才进入提问队列；仍然一次只问一个。

### 1. 改动前基线与只读审查

先固定“改动前”事实，再开始审查：

- 回退/恢复类任务先记录分支、HEAD、`git status`、`git log`、`git diff`，列出已修改、未跟踪和未提交内容。非 Git 项目改用备份、构建物和时间戳取证。
- 旧版实现只用 `git show <ref>:<path>` 读取；旧界面从历史截图、构建物或备份中取证。不要为了“看看旧版”切换分支、回滚提交或覆盖工作区。
- 建立基线矩阵：`恢复`、`保留`、`移除`、`待评估`。把布局、视觉与后台能力分开，不把“回到旧版布局”扩大成整体代码回退。
- 基线无法确认时明确缺什么证据，并用现有截图、文档或代码重建；不要把猜测写成旧版事实。

审查真实界面、代码、历史需求、开发台账、交接文档，以及明确的对标产品。覆盖：

- 信息架构、导航、层级与入口位置。
- 主旅程、空状态、加载、错误、禁用、权限不足等状态。
- 视觉语言、间距、层级、强调色、密度与一致性。
- 操作反馈、可发现性、键盘可达性与可访问性。
- 性能感知、重复渲染、布局抖动与明显的代码结构问题。

产出证据表：

| 字段 | 要求 |
|---|---|
| 观察 | 具体问题，不写“感觉不好” |
| 证据 | 截图位置或 `file:line` |
| 影响 | 对用户任务或性能的实际影响 |
| 严重度 | 阻断 / 高 / 中 / 低 |
| 置信度 | 已观察 / 推断 |

区分“已观察”和“推断”。没有证据的结论不得进入决策队列。审查结束前列出未覆盖区域，避免假装完整。

### 2. 建立决策队列

把发现转成决策，而不是转成任务清单。一个决策只解决一个轴：

- 回退 / 恢复边界：恢复哪些结构、保留哪些改造、移除哪些部分、哪些重新评估。
- 范围与优先级。
- 信息架构与导航。
- 布局与交互模型。
- 视觉语言与组件规则。
- 技术约束与迁移方式。

按依赖和影响排序：回退类任务先定“恢复 / 保留 / 移除 / 待评估”边界；其他任务先定结构与范围，再定布局与交互，最后定视觉细节。不要在信息架构未定时问按钮颜色。

每个决策准备：背景、选项、权衡、推荐、落点（文件/组件/流程）、验收标准、可逆性。

### 3. 生成可视化

根据决策类型选择图示，不能所有问题都套同一种卡片：

| 决策类型 | 必须展示 | 不能只给 |
|---|---|---|
| 信息架构 / 导航 | 真实屏幕上的结构对比、层级与入口位置 | 文字树状列表 |
| 视觉语言 | 同一真实内容的前后并排、关键 token 标注 | 孤立色板 |
| 交互 / 状态 | 关键步骤 storyboard，含空、载入、错误、禁用态 | 单个成功态截图 |
| 范围 / 优先级 | 影响地图、“做/不做”边界 | 纯文字清单 |
| 技术约束 | 架构或数据流图，附成本与风险 | 口头承诺 |

可视化要求：

- 优先使用当前环境的内联可视化能力（如 `present_visualization`）；不可用时再用 HTML 或带标注截图。
- 使用真实界面上下文和真实比例；不要用与产品无关的网页模板冒充。
- 优先前后对比或 A/B 并排，标出差异点。
- 每个选项写清：改什么、不改什么、牺牲什么、影响哪些落点、推荐理由。
- 一张图只承载一个决策，避免多问题仪表盘。
- 不用颜色作为唯一编码；交互方案要包含焦点态和键盘路径。
- 纯示意必须标注“示意”，不能让人误以为是已实现效果。
- 可视化工具不可用时，退回带标注的真实截图，并明确说明降级；禁止静默改成纯文字。

**内联可视化打包（`present_visualization`）**

- 输出目录使用工具声明的 `visualizationOutputDirectory`；`path` 只能是 `visualizations/<name>.html`。
- 文件必须是纯 HTML fragment：不要包含 `doctype`、`html`、`head`、`body`，样式与脚本直接内嵌。
- 截图先缩放或压缩，再以 data URI 内嵌；总文件小于 1 MB，目标不超过 600 KB。原图或整页 HTML 直接嵌入容易触发 `invalid`。
- 例如 macOS 可先生成缩放副本：`sips -Z 760 <old.png>`、`sips -Z 900 <current.png>`，再编码进 fragment。
- 工具返回 `{"code":"invalid",...}` 时，依次检查路径、fragment 结构、文件体积，缩小图片或拆分视图后重试；不要静默退回纯文字。
- 工具成功只证明快照已保存，不证明客户端渲染已验证；正文仍要说清这一点。

### 4. 只问一个问题

问题必须满足：

- 一句话，只包含一个决策轴。
- 2–4 个互斥选项，推荐项排第一，保留“其他”。
- 选项的代价和影响放在可视化里，不塞进问题。
- 不出现“同时”“另外”“以及要不要”这类复合问法。
- 不重复询问代码或文档里已有答案的事实。

如果回答引出新的歧义，下一轮只追问那个新问题。不要在同一轮补问第二个。

用户说“你定”时，给出推荐并记录为“委托决策”，仍要在写入前确认一次。

### 5. 记录决策

每次回答后立刻更新台账，并复述一句“这意味着……”。模板：

| ID | 决策问题 | 选项 | 用户选择 | 理由 / 约束 | 落点 | 验收标准 | 状态 |
|---|---|---|---|---|---|---|---|
| D-01 | 活动面板如何强调？ | A 系统强调色描边 / B 无边框 | A | 与系统蓝一致，降低视觉冲突 | `ActivePane` 组件 | 仅用系统强调色，键盘焦点可见 | confirmed |

状态使用：`proposed`、`confirmed`、`delegated`、`superseded`、`deferred`。

用户改口时，把旧决策标为 `superseded`，检查依赖它的决策是否失效，不要悄悄覆盖。

### 6. 收敛与信心门槛

持续单问，直到同时满足：

- 能用一句话说清目标用户和首要任务。
- 能列出已确认决策和被明确拒绝的选项。
- 能说清哪些内容不改。
- 每个改动都有落点和可观察的验收标准。
- 没有悬空的高影响未知项。

剩下的低风险默认值可以列为“显式假设”，一次说清并请用户确认；不要把假设藏进实施细节。用户喊停时立即停止提问，汇报未关闭项。

### 7. 写规格与计划

只有获得明确的写入授权后才落盘。规格至少包含：

- 目标、非目标、目标用户、成功标准。
- 已确认决策，逐条引用决策 ID。
- 关键流程与状态：空、加载、错误、禁用、权限不足。
- 视觉与交互规则，包含键盘和可访问性要求。
- 每个改动的落点、验收标准、迁移与回滚方式。

实施计划按依赖排序，标注每个任务对应的决策 ID 和验证方式。需要时交给规划或 TDD 技能执行，不要在本技能里重复实现方法论。

### 8. 实施边界

实施只覆盖已确认决策。出现以下情况时暂停并重新进入单问确认：

- 新证据推翻了已确认决策。
- 需要改动范围外文件或公共接口。
- 验收标准无法在不改变决策的情况下满足。

汇报偏差时引用决策 ID，说明影响和待确认项。

## 授权门禁

三个授权彼此独立，不能合并推断：

1. **决策确认**：用户选择了某个方案。
2. **写入授权**：用户明确同意写规格或计划文件。
3. **实施授权**：用户明确同意开始改代码。

“采纳推荐”“看起来不错”“按你说的来”只算第 1 层。除非用户在同一句话里明确授权写入或实施，否则停在第 1 层。

用户主动要求跳过确认时，记录为显式豁免，写清跳过了哪些决策和风险，再请求写入授权；不要因为赶时间就静默跳过。

## 反模式

- 用纯文字列选项，让用户“回复 A 或 B”。
- 一轮抛出五个问题，或把问题藏进长文末尾。
- 边审查边改代码，用实现代替确认。
- 没有可视化就宣布“方案已确认”。
- 把“已采纳”当成“可以写文件”。
- 可视化与真实产品脱节，或用示意冒充实现。
- 决策台账只在脑子里，规格与确认结果对不上。
- 用 `git reset --hard`、`git checkout --`、`git clean` 或覆盖工作区来完成“回退”。
- 把布局回退扩大成整体代码回退，丢掉未提交的状态、性能或安全改造。
- 把整页 HTML 或未经缩放的原图直接交给 `present_visualization`，失败后改用纯文字。
- 为了走流程，给每个小改动都开一轮确认；应先按影响分级。

## 完成前自检

- [ ] 首轮是否只读审查，没有修改项目文件？
- [ ] 回退/恢复类任务是否先记录 HEAD、工作区状态与旧版基线，且没有做破坏性回退？
- [ ] 是否把恢复边界拆成恢复 / 保留 / 移除 / 待评估，而不是整体回退？
- [ ] 每个待确认决策是否都有可视化，而不是纯文字选项？
- [ ] 内联可视化是否是纯 fragment、路径正确、图片已缩放压缩并低于 1 MB？
- [ ] 每轮是否恰好只有一个问题？
- [ ] 选择、写入、实施三层授权是否分开？
- [ ] 决策台账是否包含 ID、落点、验收标准和状态？
- [ ] 规格中的每项改动是否能追溯到决策 ID？
- [ ] 未覆盖区域、显式假设和未关闭项是否已列出？

## 资源

本技能不预置脚本或模板文件。保持流程轻量；只有在正文超过 500 行或反复出现台账格式漂移时，才按需新增台账模板或决策卡模板。
