# 双轴代码审查

对 diff 沿两条**独立轴**审查，分别报告，绝不混合：

- **标准轴**：代码是否遵循本仓库的编码规范？
- **规格轴**：代码是否实现了原始需求/spec 所要求的？

分开是核心设计——一个变更可以通过一个轴而在另一个轴失败，混合判定会让一个掩盖另一个。

## 标准轴

检查 diff 是否符合：
1. **仓库自有规范**：`CODING_STANDARDS.md`、`CONTRIBUTING.md`、或项目约定
2. **异味基线**（Fowler 12 种代码异味作为兜底）：
   - 神秘命名、重复代码、功能嫉妒、数据泥团
   - 过长函数、过大类、发散式变化、霰弹式修改
   - 依恋情结、数据类、被拒绝的遗赠、注释

规则：
- 仓库自有规范**总是覆盖**异味基线
- 每种异味是**判断**，不是硬性违规

## 规格轴

检查 diff 是否忠实实现了原始需求：
- 找到 spec（`docs/specs/` 下、commit message 中的引用、或用户指定）
- 逐条对照用户故事/验收标准
- 标记：遗漏的需求、偷渡的范围蔓延

如果找不到 spec → 报告"无可用 spec"，不编造需求。

## 执行流程

1. **锚定基准点**：确认 diff 的起止点（commit/branch/tag），空 diff 则快速失败
2. **标准轴审查**：独立分析，产出标准轴发现
3. **规格轴审查**：独立分析，产出规格轴发现
4. **输出报告**：两个轴各自独立呈现

## 输出格式

```md
## 标准轴

**总结**: {一句话概括}

### 发现
- [严重] ...
- [建议] ...

## 规格轴

**总结**: {一句话概括}

### 发现
- [遗漏] ...
- [范围蔓延] ...
```

## 工作流定位

```
grill-with-docs → to-spec → to-tickets → implement → code-review
```

本技能是构建链的**最后一步**。`implement` 在提交前内部调用本技能做审查。也可独立使用：任何时候有 diff 需要评判。
