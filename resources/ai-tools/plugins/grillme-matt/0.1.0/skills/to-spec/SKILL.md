# 讨论 → 规格说明书

将当前对话中已达成的共识和代码库理解**综合**为一份规格说明书。

**不再重新访谈。** 到达本技能时，对齐工作已经完成——本技能是综合已知信息，不是再问一轮问题。

## 前置条件

- 已经通过 `grill-with-docs` 或充分讨论达成了共识
- 如果 `CONTEXT.md` 存在，使用其中的规范术语

## 规格说明书包含

1. **问题陈述** — 什么坏了/缺了，为什么值得解决。用项目自己的词汇。
2. **方案概述** — 高层形状，不涉及实现细节。
3. **用户故事** — 详尽的、编号的具体行为列表，每条可独立验证。
4. **已定决策** — 对话中已敲定的选择，避免后续翻案。
5. **测试决策** — 在哪些接缝处测试，"完成"长什么样。
6. **明确不做** — 本次变更刻意不覆盖的范围，保持边界清晰。
7. **补充说明** — 不属于以上分类但值得携带的信息。

## 深模块思维

写规格前，先勾勒**接缝**（seam）——功能将被测试的稳定接口：
- 优先复用已有接缝，而非新建
- 尽可能用最高的接缝，理想情况整个变更只跨一个接缝
- 好的接口让测试有持久靶心，底层代码变了测试不用动

## 输出位置

将规格说明书写入 `docs/specs/` 目录（不存在则创建），文件名格式：
`docs/specs/YYYY-MM-DD-简短描述.md`

## 工作流定位

```
grill-with-docs → to-spec → to-tickets → implement → code-review
```

本技能在共识达成之后、拆分任务之前。产出的 spec 供 `to-tickets` 切分为垂直切片任务。
