# 领域建模

主动构建和打磨项目的领域模型。这是**主动**纪律——质疑术语、发明边界场景、在术语和决策结晶的瞬间就写下来。

（仅仅*读取* `CONTEXT.md` 获取词汇不是本技能——那只是任何技能都可以做的一行习惯。本技能用于你在**改变**模型时，而非仅仅消费它。）

## 文件结构

大多数项目只有一个上下文：

```
/
├── CONTEXT.md          ← 术语表（纯词汇，无实现）
├── docs/
│   └── adr/
│       ├── 0001-xxx.md
│       └── 0002-xxx.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，说明项目有多个上下文（限界上下文），地图指向各自位置。

**惰性创建**——没有内容就不建文件。第一个术语确定时才创建 `CONTEXT.md`，第一条 ADR 需要时才创建 `docs/adr/`。

## 会话中的纪律

### 质疑术语表
用户使用的词与 `CONTEXT.md` 中已有定义冲突时，立刻指出：
> "你的术语表把'取消'定义为 X，但你现在似乎指的是 Y——到底是哪个？"

### 打磨模糊语言
用户使用含糊或多义词时，提出精确的规范术语：
> "你说的'账户'——是指 Customer（客户）还是 User（用户）？这是两个不同的东西。"

### 用具体场景压力测试
讨论领域关系时，发明具体场景来探测边界：
> "如果一个订单包含3个商品，用户只想退其中1个，你的'取消'概念能覆盖吗？"

### 与代码交叉验证
用户陈述某事如何工作时，去代码里验证。发现矛盾就摆出来：
> "代码里是整单取消，但你刚说支持部分取消——哪个是对的？"

### 即时更新 CONTEXT.md
术语一旦敲定，**当场**更新 `CONTEXT.md`，不攒批。格式见 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。

`CONTEXT.md` 必须是纯术语表——不是规格说明、不是草稿纸、不是实现决策的容器。

### 谨慎提议 ADR
仅当三条全满足时才提议（难以逆转 + 无上下文会困惑 + 真实取舍）。格式见 [ADR-FORMAT.md](./ADR-FORMAT.md)。
