# 测试驱动开发（红-绿-重构）

测试先行，一次一个行为，通过红-绿循环逐步驱动代码生长。

## 核心纪律

**绝不**一次性写完所有测试。批量先写测试（"水平切片"）产出的是对**想象中行为**的测试——它们检查形状，对真实变化麻木。

正确做法是垂直切片：一个测试 → 刚好让它过的代码 → 下一个测试。每一轮都被上一轮教会你的东西所塑造。

## 红-绿循环

```
┌─────────────────────────────────────────┐
│  1. RED：写一个失败的测试（一个行为）     │
│  2. GREEN：写刚好让它通过的代码           │
│  3. 重复：下一个行为                      │
│  4. REFACTOR：全套绿了之后才重构          │
└─────────────────────────────────────────┘
```

- **第一轮是示踪弹**：一个测试证明单条路径端到端能走通，然后再向外扩展。
- **重构只在绿时做**：红了就修，不在红时重构。

## 测试质量标准

1. **读起来像规格**："用户可以用有效购物车结账"，而非"测试 checkout 函数返回 200"
2. **只测公共接口**：重命名内部函数不应该破坏任何测试
3. **期望值来自独立真相源**：已知正确的字面量、手算的例子、规格文档——绝不以代码计算的方式重新计算（那叫**同义反复测试**，天生就过，什么也没验证）

## 运行节奏

- 写一个测试 → 跑那一个测试文件
- 绿了 → 写下一个
- 全部写完 → 跑完整测试套件
- 全绿 → 重构 → 再跑完整套件确认没破坏

## 工作流定位

```
grill-with-docs → to-spec → to-tickets → implement → code-review
```

`tdd` 是 `implement` 内部的引擎——implement 驱动 tdd 来逐任务构建。也可以直接使用：当有具体行为要构建但不需要完整 spec 时，直接 `/tdd`。
