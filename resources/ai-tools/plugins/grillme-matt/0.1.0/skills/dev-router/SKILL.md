# 开发工作流路由器

你是构建链的调度中心。用户描述需求或困惑时，判断他们处于哪个阶段，路由到正确的技能。

## 构建链全景

```
grill-with-docs → to-spec → to-tickets → implement → code-review
     ↑                                         ↑
     │                                         │
domain-modeling（全程联动）              tdd（内部引擎）
```

## 路由决策树

收到用户输入后，按以下顺序判断：

### 1. 需求还模糊？→ `grill-with-docs`
**信号**：
- "我想做一个……但还没想清楚"
- "帮我审一下这个方案"
- "需求还不清晰"
- 描述中充满"可能""也许""大概""或者"
- 没有明确的验收标准

**动作**：启动拷问式对齐，逐条追问直到共识达成。

### 2. 共识已有，需要落笔？→ `to-spec`
**信号**：
- "我们讨论得差不多了，写个spec"
- "把刚才的对齐整理成文档"
- 对话中已有明确的决策和术语
- 用户说"就这样吧，开始写"

**动作**：综合已有共识为规格说明书，不再重新访谈。

### 3. Spec 已有，需要拆分？→ `to-tickets`
**信号**：
- "spec写好了，怎么拆？"
- "这个功能太大了，分一下"
- 已有 `docs/specs/` 下的文件
- 用户说"拆成任务""分工"

**动作**：将 spec 切分为示踪弹式垂直切片任务。

### 4. 任务已有，准备编码？→ `implement`
**信号**：
- "开始写代码吧"
- "按这个spec实现"
- 已有 `.scratch/*/tickets/` 下的任务文件
- 用户说"implement""构建""开发这个"

**动作**：驱动 TDD 逐任务构建，收尾审查提交。

### 5. 代码已写，需要审查？→ `code-review`
**信号**：
- "帮我看看代码"
- "review 一下"
- "这个 PR 怎么样"
- 有 diff 需要评判

**动作**：双轴审查（标准轴 + 规格轴），独立报告。

### 6. 只想测试驱动写一个小功能？→ `tdd`
**信号**：
- "帮我用 TDD 写这个"
- "先写测试"
- 具体行为已明确，不需要完整 spec
- 修一个 bug，想测试先行

**动作**：直接进入红-绿-重构循环。

### 7. 需要敲定术语/记录决策？→ `domain-modeling`
**信号**：
- "这个词到底什么意思？"
- "记录一下这个架构决策"
- "CONTEXT.md 需要更新"
- 讨论中发现术语混乱

**动作**：主动打磨领域模型，更新 CONTEXT.md / ADR。

## 快捷判断：一句话路由

| 用户说的话 | 路由到 |
|-----------|--------|
| "我想做X但没想好" | grill-with-docs |
| "对齐完了，写spec" | to-spec |
| "spec好了，拆任务" | to-tickets |
| "任务有了，开干" | implement |
| "代码写了，帮我审" | code-review |
| "用TDD写这个小功能" | tdd |
| "这个术语什么意思" | domain-modeling |
| "下一步该干嘛" | 检查项目状态后建议 |

## 状态感知

当用户问"下一步该干嘛"时，主动检查项目状态：

1. 有 `CONTEXT.md`？→ 术语已部分沉淀
2. 有 `docs/specs/` 下的文件？→ spec 已写
3. 有 `.scratch/*/tickets/`？→ 任务已拆分
4. 有未提交的 diff？→ 可能需要 review
5. 都没有？→ 从 grill-with-docs 开始

然后给出建议：
> "当前状态：{已完成的阶段}。建议下一步：{技能名} — {一句话理由}。"

## 跨阶段跳转

用户随时可以跳转，不必严格线性：
- 实现中发现 spec 有漏洞 → 暂停，回到 grill-with-docs 补齐
- 审查发现术语不一致 → 调用 domain-modeling 修正
- 小改动不需要完整链 → 直接 tdd 或 code-review

路由器的职责是**建议**，不是**强制**。用户明确指定技能时，直接执行。
