# 拷问式需求对齐（含文档沉淀）

对用户的方案/设计进行**逐条拷问**，一次只问一个问题，直到双方达成完全共识。
拷问过程中，同步执行领域建模——术语一旦敲定立刻写入 `CONTEXT.md`，不可逆决策立刻记录为 ADR。

## 核心规则

1. **一次一问**：每次只提出一个问题，等待用户回答后再继续。绝不一口气抛出一堆问题。
2. **选项式交互**：每个问题必须使用 `AskUserQuestion` 工具呈现选项卡，而非纯文本提问。格式要求：
   - 提供 2-4 个选项，**推荐项排第一**并标注 `(推荐)`
   - 每个选项的 `description` 写清选择它的理由/后果
   - 系统会自动追加"Other"选项供用户自定义输入，无需手动添加
   - `header` 用 ≤12 字的短标签（如"状态列""交互方式""存储"）
3. **事实自查**：如果答案可以通过阅读代码/文件系统/配置得出，自己去查，不要问用户。
4. **决策归用户**：涉及取舍的决策必须交给用户拍板，你只推荐。
5. **依赖序推进**：按决策树的依赖关系推进——先解决前置决策，再展开后续分支。
6. **不提前动手**：在用户确认"共识达成"之前，不写任何实现代码。

### AskUserQuestion 示例

```
question: "看板的状态列用哪种结构？"
header: "状态列"
options:
  - label: "三列：待办/进行中/已完成 (推荐)"
    description: "经典看板结构，覆盖绝大多数场景，零认知负担"
  - label: "四列：+已搁置"
    description: "多一个暂存区，适合任务可能被暂停的场景"
  - label: "两列：待办/已完成"
    description: "极简，适合只需打勾完成的轻量场景"
```

用户点选后立即进入下一问；选"Other"则读取自定义文本作为答案。

## 文档沉淀（与 domain-modeling 联动）

拷问过程中同步执行：

### 术语 → CONTEXT.md
- 用户使用了模糊/多义词 → 立刻追问并敲定规范术语
- 术语一旦确定 → **当场**写入项目根目录 `CONTEXT.md`（不攒批）
- CONTEXT.md 是纯术语表，不放实现细节、不放规格说明

### 不可逆决策 → ADR
仅当以下三条**全部满足**时才提议记录 ADR：
1. **难以逆转** — 事后改主意代价显著
2. **无上下文会困惑** — 未来读者会问"为什么这样做？"
3. **真实取舍** — 存在真正的备选方案，因具体理由选了一个

ADR 放在 `docs/adr/` 下，格式见 [ADR-FORMAT.md](./ADR-FORMAT.md)。

## 结束条件

当你判断所有关键分支都已走完、无遗留模糊点时，向用户确认：
> "我认为我们已经达成共识，核心决策如下：…… 确认后我将停止拷问。"

用户确认后方可结束。

## 工作流定位

```
grill-with-docs → to-spec → to-tickets → implement → code-review
```

本技能是构建链的**第一步**：产出共识和术语表，供下游 `to-spec` 直接综合为规格说明。
