# V0.8.0 需求审查报告

> **日期：** 2026-10-17
> **审查对象：** 项目全部需求/设计/交接文档（37 份 spec + plan、3 份交接、README、CHANGELOG）
> **审查目的：** 判定「V0.8.0 作为面向普通用户的测试版」的可行性，厘清方向再动手
> **结论摘要：** 项目不缺功能，缺**需求基线**。当前所有文档都是「开发过程记录」，没有一份定义「谁用、解决什么、做到什么程度算完成」。这是「完成度不符合预期」的结构性根因。

## 2. 审查发现

### 2.1 致命：面向普通用户的硬门槛全部未满足

这是「不符合预期」最直接的原因。以下每一项都会让普通用户**装上就用不了**：

| # | 门槛 | 现状 | 证据 | 影响 |
|---|------|------|------|------|
| A | **正式版打不出来** | `cargo build --release` 直接编译失败 | `Cargo.toml:20` `lto = true` + Homebrew rustc 1.96.1 → `mis-aligned LINKEDIT string pool`，serde_derive 无法 dlopen | 只能发 Debug 包 |
| B | **发的是 Debug 构建** | 打包脚本硬编码 `CONFIGURATION="Debug"` | `scripts/package-beta.sh:33` | 无优化、含断言、41 MB 静态库随包 |
| C | **Gatekeeper 拦截** | ad-hoc 签名，无公证、无 Developer ID | `ENABLE_HARDENED_RUNTIME = NO`；`CODE_SIGN_IDENTITY = "-"` | 双击打不开，需右键→打开 |
| D | **系统权限未声明** | Info.plist 无任何 `NS*UsageDescription` | `Resources/Info.plist`（全文 28 行，无 usage 键） | **默认收藏「桌面/文档/下载」在 macOS 14+ 首次运行即无权限** |
| E | **仅 Apple Silicon** | `ARCHS=arm64 ONLY_ACTIVE_ARCH=YES` | pbxproj / 构建命令 | Intel Mac 用户完全不可用 |
| F | **版本号自相矛盾** | 工程 0.7.4、Release 标 0.7.6、包名 0.8.0-beta.1 | `project.pbxproj:680` `MARKETING_VERSION = 0.7.4` | 「关于」页显示错误版本，问题反馈无法定位 |
| G | **无崩溃上报** | 无 crash handler、无上报通道 | `grep NSSetUncaughtExceptionHandler` = 0 命中 | 测试期用户的崩溃你看不到 |
| H | **无自动更新** | 无 Sparkle、无自研检查 | 全项目无相关代码 | 每版都要用户手动重下 |
| I | **无首次启动引导** | 无双栏用法说明、无权限引导 | 无 onboarding 代码 | 用户打开即面对双面板 + 空收藏，不知从何下手 |

**其中 D 是最致命的**：一个文件管理器，首次运行三个默认收藏全部无权限，用户会直接判定「这软件坏了」。而当前所有文档都没提这件事。

### 2.2 严重：需求基线缺失 → 结构性返工

| 指标 | 数值 | 解读 |
|------|------|------|
| 开发周期 | 44 天（2026-07-17 → 08-30） | — |
| 提交总数 | 297 | 平均 6.75 次/天 |
| `feat` vs `fix` | 108 : 80 | **每 1.35 个功能就产生 1 个修复**，返工率极高 |
| UI 重设计轮次 | **12 轮** | v0.6.5→0.6.6→0.6.7→0.6.9→0.7.0→0.7.1(五轮)→0.7.2→0.7.3→0.7.4→0.8.0 |
| 设计文档 | 37 份 | 平均 8 次提交就写一份新设计 |

12 轮 UI 重设计的本质是：**在视觉层反复迭代，却从未定义功能边界**。每次「不符合预期」都被翻译成「再调一次视觉」，于是 v0.6.5 仿访达 → v0.6.6 仿访达完整版 → v0.6.7 全应用重设计，三轮做的其实是同一件事。

### 2.3 中等：三处真源互相矛盾

| 事实 | HTML 交接 | HANDOVER.md | README | 工程实际 |
|------|-----------|-------------|--------|----------|
| 最新版本 | v0.7.2 | 0.8.0-WIP | v0.7.6 | `MARKETING_VERSION = 0.7.4` |
| 测试数 | 未记 | Rust 200 / Swift 115 | 未记 | 实跑 Rust 200 / Swift 115 ✓ |
| 构建命令 | `-scheme` | `-target` | `-target` | **无该 scheme，`-scheme` 必失败** |
| AI 打标 | 已实现 | 规则引擎 | 已实现（含 LLM 规划） | **纯扩展名规则，无 AI** |
| 本地路径 | 旧路径 | 新路径 | 旧路径 | 新路径 |

**README 的「AI 智能打标：支持 OpenAI / Claude / Ollama」与实现不符**。规则引擎叫「AI」会直接损害测试版口碑。

## 3. 已有资产盘点（不建议推倒重来）

必须说清楚：这个项目的**内核是可靠的**，问题在外壳与发行层。

| 资产 | 状态 | 说明 |
|------|------|------|
| Rust Core（14 模块，42 个 FFI 函数） | **可靠** | 200 项单测全绿；bulk_read / dedup / task_scheduler / path_guard 都已实战 |
| Swift 115 项测试 | **可靠** | 覆盖 PaneState / 详情栏 / 键盘 / 侧边栏 / 冻结填充 |
| 双栏架构 + 视图抽象（`FFPaneActionsController`） | **已重构过** | FileListView/FileGridView 操作逻辑已统一，这层不用再动 |
| 标签双写（自有 xattr + macOS 原生） | **可用** | 与访达双向可见 |
| SMB 挂载 + 健康检查 + 退避重连 | **可用** | Swift 侧实现，未走 Rust |
| 液态玻璃 / 超椭圆 / 主题三态 | **视觉已达水准** | 12 轮迭代的成果，不该丢 |
| 打包脚本（DMG/ZIP/SHA256） | **可用** | 只差 Release 构建与签名 |

**结论：不需要重写。需要的是「收口」——把已有能力收进一条可发布、可验证、可维护的轨道。**

## 4. 我建议的「普通用户测试版」准入标准

这是当前**完全缺失**的东西。建议作为 V0.8.0 的验收基线：

### Must（不满足就不叫测试版）

| # | 标准 | 验证方式 |
|---|------|----------|
| M1 | Release 构建可复现（关 LTO 已实测通过） | `bash scripts/build-rust.sh Release` + `xcodebuild -configuration Release` 成功 |
| M2 | 版本号单一真源（0.8.0 / 8000） | 工程、Info.plist、DMG、关于页四处一致 |
| M3 | 首次运行三个默认收藏可读 | 全新用户账号虚拟机实测，或 `tccutil reset` 后实测 |
| M4 | 声明 TCC 用途说明 + 权限缺失有人话引导 | Info.plist 含 5 个 usage 键；无权限时给出「如何在系统设置授权」提示 |
| M5 | 无崩溃、布局冲突日志为 0 | 冷启动 + 20 项常规操作，`log show` 无 constraint 冲突 |
| M6 | 关键路径错误有用户可读提示（非英文 NSError 原文） | 复制到只读卷、拖拽无权限目录、网络卷掉线三种场景 |
| M7 | Debug 日志不进发行包 | Release 编译时 `#if DEBUG` 隔离 |
| M8 | 打包产物可安装（DMG 拖拽 + 首次打开说明） | 在干净机器上装一次 |

### Should（测试版应该有）

| # | 标准 | 说明 |
|---|------|------|
| S1 | Developer ID 签名 + 公证 | 需你的 Apple 开发者账号；没有则退化为「右键打开」+ 图文说明 |
| S2 | 崩溃上报（至少本地日志 + 一键导出） | 测试期收集问题的唯一手段 |
| S3 | README 宣称与实现对齐（删「AI 打标」） | 口碑风险 |
| S4 | 首次启动引导（3 屏：双栏、权限、快捷键） | 降低劝退率 |
| S5 | Intel 支持或明确标注「仅 Apple Silicon」 | 明确标注即可，不一定做 Universal |
| S6 | 96 条编译警告清零 | 主要是 selector 字符串化改造 |

### Defer（V0.8.0 明确不做）

Universal 二进制、自动更新、多语言、LLM 打标、WinRAR 类格式支持、插件系统。

## 5. 需要拍板的决策

见对话中的单选确认。核心分歧是：**V0.8.0 是「先能装能用」还是「先把架构理干净」**。

我的倾向：**发行工程化（M1–M8）为必做主线，架构重构只做「挡住 bug 修复」的最小切片**，理由是——你现在的痛点是「完成度不够、给不了普通用户」，而 12 轮 UI 重设计已经证明：不动需求基线只动代码，会继续返工。
