## 0. 为什么需要这份文件

项目此前有 20 份按日期堆叠的设计稿，每份都是「这一轮改什么」，没有任何一份定义「什么算改对了」。后果是视觉基准在 18 天内换了 6 次：

```
07-20 完整重构 → 07-22 访达风格 → 07-27 访达重设计
→ 07-28 克隆访达 → 07-29 全面重设计 → 08-04 液态玻璃
```

其中 08-04 的记录是「液态玻璃不符合预期、没有浮动在操作区上方的玻璃效果」——那时要的是更多玻璃，而访达没有液态玻璃。这与 07-28 的「完全克隆访达」本身互斥。两条都被写进了「硬约束」，于是每一轮都可以合法地推翻上一轮。

本文件的作用：**把「对标访达」和「产品自主」分开，各自给出可判定的规格**。分开之后，「不像访达」不再能用来否定一个产品自主决策。

## 1. 两类基准

| 类别 | 含义 | 判定方式 |
|---|---|---|
| **对标访达** | 材质、选中态、字号、行高、侧栏结构、列头、分组、面包屑、详情栏内容项 | 必须与访达视觉一致，可测量 |
| **产品自主** | 双行工具栏 72pt、双操作区、详情栏浮层高度、设备浮层、标签药丸 | 不要求像访达，按本文件规格；**不得以「不像访达」为由返工** |

判定标记：

- ✅ 符合，不动
- ⚠️ 有偏差，需调整
- ❌ 设计冲突，待裁定
- 🔧 实现与设计不符（缺陷）

## 2. 审查发现的五处硬伤

这五条不是审美问题，是设计体系缺少单一来源。

| # | 硬伤 | 实测 | 后果 |
|---|---|---|---|
| **H1** | **两套字体令牌并存** | `FFDesign.Typography`（10 / 11 / 11sb / 13sb，`DesignTokens.swift:129-135`）与 `FFDesign.Text`（17 / 15 / 13 / 12 / 11 / 10 / mono12，`DesignTokens.swift:315-335`）同时存在 | 同一信息档两处取值不同，无法判定该用哪个 |
| **H2** | **129 处硬编码字号** | 11pt×60、12pt×28、10pt×21、13pt×11、14pt×3、9pt×2、15pt×2、17pt×1、20pt×1 | 令牌形同虚设，是「看起来不统一」的直接来源 |
| **H3** | **侧栏实际 200pt** | `DesignTokens.swift:289 sidebarWidth = 200` | 历史文档多处写 220pt，数值错误 |
| **H4** | **列表行高有三档** | 基准 22 / 26 / 32，带标签 42 / 48 / 56（`FFCommon.swift:138-153`） | 历史文档只记 26 / 48，遗漏密度档位 |
| **H5** | **README 卖点与实现相反** | README 称「玻璃态双栏、NSVisualEffectView 系统级毛玻璃」为核心卖点；实际操作区是实体 `#F5F5F5` / `#2D2D2D` | 对外承诺与产品不符 |

| 4 | B-06 标准位置专属图标（若裁定要做） | 裁定 | 截图对照访达 |
| 5 | F-02 空态接入、F-03/F-04 错误与权限人话化 | 阶段 D 进行中 | 断网 / 清 TCC 实测 |

> 批次 1 与 2 必须分开：一次改完会让「字号变了」和「布局变了」混在一起，无法定位回归。这是过去 12 轮返工的典型成因。

## 17. 冻结规则

批次 1–3 完成后，本文件的令牌表生效。此后：

1. 任何视觉改动必须指向表中某一条，且只改那一条
2. 出现「不符合预期」时，先定位是表中哪条不达标，再定点修
3. **禁止整体重设计**，确需重做须用户显式同意并在 §18 登记
