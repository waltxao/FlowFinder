> **版本：** 1.0
> **建立日期：** 2026-10-17
> **适用范围：** v0.8.0 及后续版本
> **性质：** 本项目**唯一需求真源**。与任何历史 spec、plan、README、交接文档冲突时，以本文件为准。
> **编写依据：** v0.6.0 ~ v0.8.0-P1 全部 37 份设计文档、CHANGELOG 全部版本条目、`docs/HANDOVER.md`、以及各版本发布后用户逐条验收反馈。

## 0. 这份文档为什么存在

项目此前**没有需求文档**，只有开发过程记录。这导致了三个可量化后果：

| 现象 | 数据 | 根因 |
|------|------|------|
| 返工率极高 | 44 天 297 次提交，`feat` 108 : `fix` 80 | 每 1.35 个功能就产生 1 个修复 |
| UI 反复重设计 | 12 轮（v0.6.5 → v0.8.0） | 没有「视觉验收标准」，只能每轮重新猜 |
| 需求被静默推翻 | v0.8.0-P0 一次推翻 3 条已确认决策 | 决策散落在 spec 里，没有汇总层，改动时无从对照 |

本文件的作用：**把散落在 37 份文档里的决策收成一张对照表**。任何改动前先查这里，避免"改了一个地方、推翻三条旧决策"。

## 1. 产品定义

### 1.1 定位

**FlowFinder（流方达）是 macOS 上的原生双栏文件管理器**，为需要「同时看两个目录、批量搬文件」的人设计。

技术形态：Swift + AppKit 构建 UI，Rust Core 提供文件系统引擎，通过 C ABI（66 个 `ff_*` 导出符号）桥接。

### 1.2 目标用户

| 层级 | 用户 | 核心场景 | 关键诉求 |
|------|------|----------|----------|
| 主要 | 开发 / 运维 / 设计 | 在多个目录间搬运素材、构建产物 | 双栏对照、全键盘、大目录不卡 |
| 次要 | 从访达迁移过来的普通 Mac 用户 | 整理文件、备份 | 打开就会用，视觉与访达一致 |

### 1.3 与访达的关系（**核心需求，非可选项**）

| 维度 | 要求 | 来源 |
|------|------|------|
| 整体视觉 | **完全克隆访达** | v0.6.6 方向决策原文；2026-09-02 侧边栏 spec「硬约束」 |
| 材质架构 | 侧边栏亚克力 vibrancy + 操作区实体背景 | v0.6.7 核心架构转变 |
| 交互语义 | 与访达一致（拖拽复制/移动判定、快捷键、选中行为） | v0.6.6 / v0.7.0 |
| 产品差异 | 双栏、跨面板操作、查重、批量重命名 | v0.6.0 起 |

> ⚠️ **历史争议点已裁定**：v0.8.0-P0 曾在 `2026-10-17-v0.8.0-beta-spec.md` §1.4 写下"不追求像素级克隆访达"，理由是"12 轮迭代投入产出比低"。此结论**未经用户确认，现予撤销**。
> 12 轮重设计的真实原因是缺少验收标准，不是方向错误。方向仍然是克隆访达。

### 1.4 明确不做

- 不做访达的完整替代（不接管系统默认文件管理器、不注册"打开方式"）
- 不做云盘同步、版本控制、代码编辑
- 不做 iOS/iPadOS 协同
- v0.8.0 不做多语言（仅简体中文）
- 不做插件系统、不上 App Store

### 2.4 v0.6.7（2026-07-29）— 亚克力 + 实体架构

根因：全透明玻璃架构导致看不清、卡顿、不统一。确立**当前仍在运行的核心材质架构**：

```
窗口边框（亚克力 vibrancy）
├── 侧边栏（亚克力 .sidebar）        ← NSVisualEffectView
├── 操作区 ×2（实体 #F5F5F5 / #2D2D2D）
└── 设备浮层（实体，浮动左下角）
```

| 决策点 | 结论 |
|--------|------|
| 材质架构 | 侧边栏 + 窗口边框用亚克力，其余全部实体背景 |
| 操作区背景 | 日间 `#F5F5F5` / 夜间 `#2D2D2D` |
| 子窗口 | 全部实体背景，移除 FFGlassView |
| 主题 | 恢复三态（浅色 / 深色 / 跟随系统） |
| 设置页 | 实体背景 + 分区布局（仿系统偏好设置） |
| 详情栏图标 | 空白占位图标，选中后替换 |
| 搜索范围 | 当前目录 + 子目录本地过滤 |
| 路径栏 | 完全仿访达（固定位置、每段可点击、分隔符弹同级菜单） |
| 分组 | 粘性 header + 缩进 + 计数徽章 |
| 复制/移动反馈 | 底部状态栏进度条，不弹窗 |
| 标签同步 | 读写 `_kMDItemUserTags`，访达双向可见 |

## 9. 变更控制

1. **新增或修改需求**，先改本文件对应条目，注明版本与理由，再动代码。
2. **任何推翻历史决策的改动**，必须在 §2 找到原始条目，在提交信息里写明"覆盖 vX.Y 的某决策，理由：…"，并在 §5 登记。
3. **提交前自检**：改动是否触碰 §6 的十项硬约束。
4. **本文件与历史 spec 冲突时以本文件为准**；但历史 spec 的原始诉求在 §2 有摘要，供追溯。
