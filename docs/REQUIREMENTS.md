## 0. 与历史文档的关系

项目有 20 份按日期命名的设计稿，记录了每一轮改了什么。它们**不再具有解释权**：

| 文档 | 现在的角色 |
|---|---|
| `docs/PRODUCT.md` | 产品是什么、给谁、不做什么 |
| `docs/DESIGN-SPEC.md` | 视觉与交互的规格本体 |
| `docs/ACCEPTANCE.md` | 什么算做对了 |
| 本文件 | 当前版本要交付的需求清单与优先级 |
| `docs/HANDOVER.md` | 接手/大改前必读：架构、流程、已知债务 |

**冲突处理**：与本文件或上表前三份冲突时，以本文件为准。

## 1. 状态口径

上一版最大的问题不是缺条目，是标了大量没核对过的 ✅。本版改用四档，且**✅ 必须给实现位置**：

| 状态 | 含义 | 要求 |
|---|---|---|
| ✅ 已验证 | 代码存在且通过验收条件 | 必须给文件:行号 |
| ⚠️ 待验收 | 代码存在，未按 `ACCEPTANCE.md` 验过 | 给文件位置 |
| 🔧 不符 | 有实现但与需求不一致 | 写明差在哪 |
| ❌ 未实现 | 无实现 | 写明阻塞程度 |

优先级：**P0** 阻断发布 · **P1** 本版应做 · **P2** 可延后。

## 11. 变更控制

1. **新增或修改需求**：先改本文件，注明优先级与理由，再动代码。
2. **推翻既有决策**：在提交信息写明「覆盖 X 条，理由：…」，并在 `DESIGN-SPEC.md` §18 登记。
3. **标 ✅**：必须能给实现位置与验收条件。给不出的一律标 ⚠️ 或 🔧。
4. **视觉类改动**：必须指向 `DESIGN-SPEC.md` 令牌表某一条，禁止整体重设计。
5. **提交前自检**：是否触碰 `PRODUCT.md` §6「明确不做」与 §7「明确不追求」。
